# Answer and lifecycle handling

- Use `input_list` for eligible delivered user-message IDs. Call `input_resolve_from_message` only if `messageResolution:1`, the messages clearly answer the request, and you can supply all required values without guessing. Use exact source IDs, requestId and current expectedRevision. Assistant messages, generated form messages, undelivered text and messages from other chats are not evidence.
- Preserve the difference between the user's words and your interpretation. For partial, contradictory, ambiguous answers or “you decide the rest”, keep the request pending and ask only about the unresolved details. Do not turn permission to suggest an itinerary into a fabricated confirmation of required fields.
- `resolved` means the answer is recorded without sending the original user text again. `confirmationRequired` means the host has preserved an edited draft and proposed an interpretation. Wait for the user to accept or reject it; do not call submit or generate a replacement to escape confirmation.
- With `replace:1`, use `input_replace` for an explicitly changed requirement, supplying the current revision and a complete replacement request. Untouched requests may be replaced immediately. Edited requests produce a proposal with a reserved replacementId; that ID is not a second live form until acceptance. Do not migrate user input by guessing that identical field names have identical meanings.
- With `cancel:1`, use `input_cancel` when a request is no longer needed, with a truthful reason and current revision. This cancels the request, not the entire task, and does not mean the user answered. A user cancellation event also provides no answer. Explain limitations if the task still needs that information; do not immediately recreate the same request against the user's choice.
- On CONFLICT, refresh the relevant request once before deciding what to do. Do not overwrite drafts or retry stale revisions. On invalid input, correct only the reported schema issue; on unavailable or denied tools, offer conversational clarification rather than repeated calls. If an invocation outcome is uncertain, retry only the same idempotent command, not a new requestKey. Stop if the retry provides no new evidence.
- An answered request and its delivery receipt describe different states. `unknown` means it may already have been delivered: never automatically resend, recreate or instruct the user to submit it again. The host offers read-only verification. Held or paused inputs require the user's explicit continuation.
- Native `request_user_input` uses its own RPC response channel. Do not send its answers through supplemental tools or claim old native questions survive an application restart. Persistent forms do survive normal turn completion. `executionUnitResume:0` means independent A/B/C scheduling is not supported; continue only work you can actually perform independently in the current task.
