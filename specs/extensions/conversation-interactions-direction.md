# 对话内交互组件：方向与设计入口

状态：YAML 声明式表单与线性多步骤已进入 [具体设计](./declarative-forms-design.md)，尚未实现；更高级交互仍是探索方向。2026-10-01 已先实现 [MCP Apps 隔离任务卡片](./mcp-apps-design.md)，复用现有操作和授权路由；本页其余设想不因此自动成为已实现能力。

## 目标与示例

扩展提供业务能力，Agent 在对话中组织流程，宿主渲染结构化交互。以“财务报销助手”为例：用户新建 Task，输入“我要报销差旅费”，Agent 根据扩展 Skill 理解流程，调用扩展查询报销类别、必填项及业务规则，选择表单并提供预填值。用户补充日期、地点、金额和票据，明确点击提交后执行报销操作；提交结果显示报销单号与审批状态。

日期、金额和类别等不得仅凭模型猜测就作为用户确认值，业务规则和最终校验由扩展及业务服务提供。

## 已确认方向

- 优先采用扩展声明、宿主渲染的标准表单，保持 Apple 风格、键盘操作与一致的确认体验。Agent 负责选择、解释和预填，用户明确提交后才执行业务操作。
- 数据结构与 UI 契约分开设计。JSON Schema 不能独自表达布局、联动选项、金额币种、附件和异步校验。
- 复杂业务组件未来可考虑隔离 Web 页面，例如票据标注；MCP Apps 的首版隔离与生命周期已单独实现，仍不等同于宿主标准表单。
- 表单是持久交互实例，使用稳定 flowInstanceId（早期方向稿称 interactionId），关联 Task、扩展、业务账号、表单版本和草稿；重启或继续聊天应能恢复，重新生成回复不能重复创建业务单据。
- 用户开始编辑后，Agent 的后续修改以建议呈现，不能静默覆盖。敏感字段可只交给业务服务，不必进入模型上下文；精确的数据可见性契约待设计。
- 填表不等于授权提交。宿主控制的提交动作绑定实际内容，复用 Operation 授权与确认机制。超时后查询恢复，不自动重复提交；可复用消息动作的幂等和执行恢复原则。

## 职责

| 角色 | 职责 |
| --- | --- |
| 扩展 | 表单定义、业务校验、草稿存储、提交操作 |
| Agent | 理解意图、选择表单、建议预填值、解释规则 |
| 宿主 | 渲染、交互实例与恢复、授权确认、执行记录与结果展示 |
| 业务服务 | 最终业务校验、持久化单据与审批流程 |
