# 运行中补充信息：技术设计草案

日期：2026-10-14。状态：产品范围与五项交互规则已确认；以下为待实现技术设计，U0 施工契约已冻结，运行时尚未实现，详见 [协议](contracts/user-input/README.md) 与 [探针结果](user-input-u0-results.md)。需求见 [需求文档](user-input-requirements.md)，代码审计与验收见 [任务列表](user-input-implementation-plan.md)。本轮增加施工 Schema 和探针，未修改正式运行时或 SDK 类型。

## 架构与复用边界

三层：宿主交互层负责待补充区与历史展示；运行时负责请求、持久投递及恢复；内置 Skill 负责选择提问时机、字段和后续处理。模型必须显式调用工具，不能从普通 Markdown/代码块自动提取可执行表单。

现有 QuestionQueue 已在 Conversation.conversation-dock，位于消息滚动区之外；沿用此布局，将原生问题与持久表单投影为统一待办。授权保留独立操作类型与原有安全边界，不把授权响应降级为普通答案。

已有 forms_present 立即返回，chat_inputs 可通过 turn/steer 追加到运行轮次，空闲则 turn/start。保留该基础；逐步把仅面向表单的投递封装为带来源和投递策略的用户输入通道，不直接删除 flowId/source 校验。

## 请求和投递分离

新增宿主私有 InputRequest，字段以 U0 施工契约约束为准：

| 字段 | 用途 |
| --- | --- |
| id / revision | 宿主生成标识和 CAS 版本 |
| conversationId / runId | 绑定已有聊天身份；二者沿用现有真实映射，不凭名称认定恒等 |
| origin | native-question / model-form / skill-form；扩展来源由宿主绑定 |
| sourceRef | skill、extension 及版本；动态模型表单记录生成来源，不伪装成受信模板 |
| owner | 原 thread/turn/item 或独立 executionUnit 引用；运行时填写，不由模型指定其他聊天 |
| scope | 首版 conversation；未来 executionUnit 仅在真实能力开启后支持 |
| formRef 或 definitionSnapshot | 引用已有表单实例或已校验的动态定义，禁止双份草稿 |
| state | pending / answered / cancelled / superseded / expired |
| draft / answerSnapshot | 草稿版本、提交时字段值和标签/语言快照；复用现有表单存储时只保留引用 |
| answerSource / sourceMessageIds | 表单提交或用户文字关联；来源必须是宿主可验证的本聊天用户消息，保留解释与证据 |
| replacementProposal | 有草稿时保存替换候选及其基准 revision，用户接受后才切换 |
| submissionId / deliveryId | 唯一已提交答案与持久投递关联 |
| createdAt / updatedAt / replacesId | 历史、排序与显式替换关系 |

交互状态与投递状态独立：answered 表示用户答案已保存，不表示模型已收到，更不表示业务完成。delivery 复用 queued / dispatching / delivered / failed / unknown；UI 合并显示“已保存，等待送达”“已送达”“结果待核实”等。

提交以事务/CAS 完成：核验所属聊天、来源有效性、revision、定义与答案 → 冻结答案 → 写入唯一投递项 → 将请求置为 answered。重复提交返回同一回执，内容不一致拒绝。已持久答案但入队失败不得显示成功后丢失。

普通追加文字也拥有 clientInputId 与持久回执，但不要求伪造 form flowId。必须独立校验聊天授权、归档、运行状态和输入限制；保留表单来源校验适配器。

## 已冻结工具与内部接口（尚未开放）

以下为 U0 冻结的施工接口，尚不是当前可调用接口。完整结构见 [契约](contracts/user-input/README.md)：

- input_capabilities：返回动态表单、持久请求、异步补充与执行单元恢复的独立能力位。
- input_list：列出当前聊天待补充请求及有限的真实用户消息证据。
- input_request：接收静态模板引用或动态单页定义、提问原因、预填；宿主绑定聊天和来源。立即返回 requestId/pending，不长时间占用工具调用等待用户。
- input_read_answer：读取本聊天指定请求已冻结的答案；未回答明确返回 pending，Skill 不循环轮询。
- input_resolve_from_message：模型提供 requestId、expectedRevision、sourceMessageIds 和提取的字段值；仅对信息补充请求开放。宿主核验来源、请求用途及字段约束，不允许伪造用户消息或调用业务操作。
- input_cancel / input_replace：仅作用于合法来源且仍 pending 的请求。取消告知模型未获答案；未编辑可直接替换，有草稿则创建替换提案，用户接受才切换，旧请求与草稿保留。
- renderer submit/append：宿主 IPC 接受 requestId、expectedRevision、clientInputId、答案或普通文本；页面不可指定其他窗口身份。属于内部 API，不自动成为扩展公开 SDK。

请求创建采用宿主绑定聊天/真实来源 + requestKey 去重；现有 MCP 不传原始引擎 toolCallId，不使用传输 RPC id 代替。重复键且内容不一致拒绝；主动替换使用 requestId，不按文案相似度合并。

动态定义复用现有字段子集：text、textarea、number、money、date、select、checkbox、switch；首版一个 step，submit.kind 固定 chat。无脚本、URL、operation、隐藏输入/业务绑定、远程加载、复杂联动。日期范围用两个 date，人数用 number；现有协议无多选组件时不在示例中虚构支持。

## 运行时投递与请求适配

1. 活动轮次：按当前引擎可用能力发送 guarded turn/steer，expectedTurnId 防止误投下一轮；同一聊天串行投递。
2. preparing/结束清理：持久 queued，待边界明确后再发送。
3. 正常空闲：若投递策略允许，以原聊天 start 新轮次；延续 conversationId。
4. 用户停止：持久记录聊天投递暂停标志，阻止尚未发送的 queued 继续派发或自动 start；停止后填写仅保存草稿，明确“提交并继续”或继续任务才解除暂停。恢复哪些历史 queued 项必须在继续动作中明确展示，不能静默发送积压内容。归档/来源停用另行校验，继续任务不能绕过失效来源。发送前重查停止标志；已经 dispatching 的项目不能假定未发送，按回执或 unknown 核实处理。
5. 发送后连接断开：unknown，不自动重发；复用 client ID 和 thread/read 只读核实，未找到不是未执行的证据。
6. 原生 requestUserInput：回答仍通过原 RPC request ID 回送，不转换成 steer；呈现可以统一，协议语义不合并。收到 resolved/轮次结束/中断时及时清理。重启后的旧 RPC 不能假装可恢复，需要置失效并提供重新询问路径。
7. 动态持久请求可以跨正常轮次保留；不能照搬当前 run.questions 在轮次结束全部清空的规则。答案只在安全执行边界进入模型，不承诺即时打断正在执行的工具。

## 文字回答、取消与替换

文字关联由模型显式调用，不在前端按关键词匹配。宿主只允许引用当前聊天真实用户消息，按请求创建时的消息序列记录上下文；来源消息及字段映射随答案冻结，可供历史查看。模型的解释标记为解释，不伪装成用户原始文字。宿主能验证出处和字段类型，不能单靠 Schema 证明语义正确，内置 Skill 必须在歧义、相互矛盾或缺少必要信息时继续确认。

“预算五千，其他你安排”只能据实提取预算并记录用户允许自行安排的范围，不能据此伪造日期、付款许可或其他必填答案。部分明确字段可作为带来源的补充建议保留；未满足请求完成条件时仍 pending。文字回答与已编辑草稿冲突时不得静默覆盖，提示确认冲突字段。

文字已在当前模型上下文时，关联工具返回冻结答案回执即可，不能再把原文重复 steer/start；若有其他合法等待者需通知，按请求事件唯一 ID 投递，而非重复用户消息。原生 RPC 问题继续使用原协议回答，首版文字关联不泛化到原生授权或业务 operation 表单。

取消与“稍后填写”分开：前者终止请求并以幂等事件通知模型未获答案；后者仅改变展示。聊天已停止时取消事件保存待后续明确继续，不自动启动模型。取消不代表任务必然可继续，必要信息仍缺失时模型应解释限制。

替换使用 CAS：无用户编辑（含尚未保存的本地输入）才可直接 supersede；模型预填不算用户编辑。需由前端及时登记编辑状态/版本，不能仅因数据库草稿尚未更新而判断未编辑。有草稿则保留原 pending 请求和输入，展示候选供用户接受或拒绝。接受时校验原 revision；期间有新输入则重新确认；拒绝保留原请求。旧记录永久只读，不执行旧提交。

## 局部等待的后续模型

首版 owner 为聊天执行上下文；模型收到 requestId 及结构化答案再继续推理。这支持“先做其他独立工作”，不保证具体 B 的自动恢复。

后续引入 ExecutionUnit：稳定 id、dependsOn、checkpoint、waitingRequestIds、状态。B 进入 waitingInput；不依赖 B 的 A/C 仍 runnable；依赖 B 的 D 保持 blocked。回答事件只唤醒绑定 B，重复事件幂等；父任务全部必要节点完成后才能完成。运行状态与等待请求数量分别展示，不能看到一个问题就把全部活动执行显示为停止。

必须区分模型计划条目与可执行节点。节点依赖由规划方声明、宿主验证引用/环路/状态并执行；缺少依赖不能靠调度器猜出安全性。首版不引入完整 DAG 引擎，也不伪造 nodeId 精确路由。

## UI 与内置 Skill

统一 dock 列表显示来源、请求原因和待补充数量，一次展开一张，其他折叠，无自动提交倒计时；展开表单复用 TaskForms 字段控件。历史显示定位链接/答案摘要，共用同一实例状态。需将编辑状态上移或持久化，避免历史虚拟化卸载导致草稿丢失。收起、滚动、布局切换不得提交、取消或重建实例。

运行中 Composer 显示独立“发送补充”和“停止”；持久接受后清空本次输入快照，保留用户在发送期间新输入的文字。不能重复把同一草稿排队。授权优先级、多个待办折叠、最大高度和无障碍焦点共同验收。

内置 Skill 随应用发布、版本化，无业务服务权限：探测能力 → 判断缺失信息 → 选择少量明确字段与必要预填 → 发起请求 → 继续独立工作 → 接收带 requestId 的答案 → 读取冻结内容 → 继续任务。禁止伪造用户表单提交；允许依据真实用户消息调用受限文字关联工具。禁止盲目轮询、把答案当系统指令、在等待必要信息时伪造最终结果。Skill 不可用时宿主仍保留普通文字补充入口。

## 兼容、数据与发布

旧静态模板、operation 授权及现有 forms_* 工具保持行为。新动态工具以独立能力探测启用；业务表单进入 dock 应显式 opt-in，避免所有旧表单突然变成全局待办。动态表单文案随实例冻结，模板文案复用现有词典快照，宿主控件跟随当前语言。

迁移以当前数据库版本为基线选择下一版本，不在文档预先硬编码 user_version；老数据可读，旧 flowId 校验保留。聊天删除级联清理请求/答案/队列；归档不删除历史但阻止提交。正文、答案和敏感值不进入诊断日志。新配额已在 U0 冻结，实施时同步校验器与 SDK/CLI 文档，验收后再开放能力清单，不仅修改类型宣称功能可用。


## U8 落地：内置引导分发与禁用

内置 `supplemental-input` 随应用版本分发，通过现有技能存储发布不可变副本。稳定 ID 与整包摘要避免重复安装；更新保留用户启停状态。技能目录按需发现，正文不会重复常驻注入；执行上下文没有补充工具时不发现此内置引导。现有技能管理提供只读预览及启停，后台禁止覆盖、编辑和删除。资源不可用时退回普通聊天，第三方表单能力不依赖内置引导。具体行为与验证见 [U8 结果](user-input-u8-results.md)。

## 问答执行记录（2026-10-14）

待补充区负责填写，对话执行过程负责回溯。原生问答和持久化补充表单采用统一的 shadcn/ui Collapsible 展示，默认折叠，展开为问题与回答列表，不展示内部 JSON。

- 持久化请求由宿主写入 `turnKey`、`order`，定位到发起请求的轮次和过程位置。模型及 SDK 不得提供这两个字段，幂等重试不迁移原位置。旧记录仅在能够确定所属轮次时关联。
- 待填写记录提供“前往填写”，不复制编辑器、不显示草稿值。提交后更新同一记录，以冻结的答案和问题标签为准。
- “已提交”与投递状态分别展示：等待发送、正在发送、已送达、发送失败、送达待核实；缺失投递记录不能推断送达。
- 原生问答在发起时写入结构化消息记录，提交后原位更新，私密回答只保存遮蔽文本。RPC 失效后未回答记录显示已失效。
- 已取消或替换表单的原填写单独折叠，并明确标注未提交，不作为回答。
- 本次不新增 SDK/CLI API；宿主内部呈现元数据不进入模型工具契约。

补充工具的过程记录使用可读名称（如“读取你的回答”）；`input_read_answer` 优先使用回答快照的字段标签及原表单的选项标签展示。UUID、工具参数和嵌套 MCP 回执仅在“技术详情”二级折叠中展示。解析失败时显示友好降级说明，不将原始 JSON 当作回答，也不推断执行成功。
