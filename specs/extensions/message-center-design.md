# 消息中心设计

> 2026-10-08 实现更新：消息操作与扩展企业认证已有源码预览链路。当前可调用接口与明确限制以 [消息按钮与认证接入规范](message-actions-auth-guide.md) 为准。以下设计中的账号选择器、账号消息与其他未来能力不代表本次已实现。

状态：M2 已确认决策整理稿；接口与存储契约尚未冻结，未据此宣称功能已实现或验收通过。

本文承接 [首版范围](./scope.md) 第 8 节，集中维护消息中心详细决策。第 1～7 节为已确认结论，第 8 节为接口与字段草案，第 9 节为待评审事项。SDK 草案不得视为现有 SDK 已开放的能力。

## 1. 产品范围与接收偏好

已确认范围：消息中心统一收纳宿主和扩展产生的、需要用户关注的信息，例如任务完成、需要确认、项目邀请和风险提醒。聊天正文和执行日志保留在原页面；复杂业务内容通过消息跳转到对应扩展页面处理。

首版实现站内通知闭环：标题、纯文本正文、宿主绑定的来源、时间、类别和可选操作按钮；不支持扩展自定义 HTML。扩展只能发布、更新或撤回自己的消息。业务去重键按来源和账号范围隔离；同一用户配置下各窗口共享持久消息和已读状态。

操作按钮引用扩展声明的命令，点击时重新检查扩展状态、参数和资源授权。“已读”只表达本地阅读状态，“接受邀请”等业务确认需扩展调用服务器，成功后再更新消息，不因点击而认定成功。

支持按扩展静音、标记已读和清除消息。系统通知是可选提醒，宿主统一控制避免多窗口重复弹出，不作为首版验收前置条件。卸载后保留历史消息并禁用操作；退出业务账号后隐藏对应账号消息。清理期限和限额待定；账号消息恢复遵守第 2 节与第 6 节规则。

已确认设置入口：`设置 > 消息通知` 提供扩展来源列表和接收开关，用户可以独立允许或拒收某个扩展的消息。设置属于宿主用户偏好，由宿主统一执行，扩展不能自行修改或绕过；同一用户配置下多窗口共享。

已确认接收语义：关闭后不接收该来源的新消息，不增加未读数，也不产生站内弹出提醒或系统通知；已有历史消息保留。拒收不等同于静音，静音仍接收并保留消息，仅停止主动提醒。关闭消息接收不停止扩展后台、服务连接或其他业务能力。

已确认默认策略：用户安装并启用扩展后，默认允许站内消息；系统通知另行控制。用户重新开启接收后，拒收期间的消息默认不补投，避免旧消息集中涌入。SDK 拒收结果，以及防止扩展重投绕过接收偏好的协议细节，仍需在详细设计中确定。

### 消息偏好作用范围

1. 扩展接收开关按 Profile + 扩展保存，覆盖该扩展的本地消息及所有业务账号消息；切换业务账号不能绕过拒收。
2. 首版不提供按业务账号分别设置的接收开关。
3. 平台自身消息作为独立来源管理。当前操作必须显示的授权确认、执行错误仍在原界面反馈，不受消息中心拒收影响；这不构成向消息中心强行发布通知的例外。

### 设置数据归属

| 设置类型 | 保存范围 | 切换扩展业务账号时 |
| --- | --- | --- |
| 宿主管理偏好：消息接收、静音、扩展启停 | Profile + 扩展 | 保持不变，由宿主管理 |
| 扩展通用配置：本地工具路径、界面偏好 | Profile + 扩展 | 保持不变 |
| 扩展账号配置：当前团队、账号专属选项 | Profile + 扩展 + 业务账号 | 使用对应账号的数据 |
| 账号凭据 | 对应账号范围内的专用秘密存储 | 使用对应账号的凭据，不写入普通配置 |

扩展设置规范须明确配置项的作用范围，避免账号配置误存为通用配置；具体声明字段与接口待详细设计。首版消息接收仅提供扩展总开关，不提供账号子开关。例如关闭 PM 消息后，在同一 Profile 内从 PM 账号 A 切换到 B，B 的新消息仍被拒收；这不会将 A 的业务配置或凭据共享给 B。

## 2. 本地 Profile、账号与会话

### 本地 Profile 与可选认证模型（取代讨论中“切换平台账号就切换整套扩展后台”的建议）

1. 本地 Profile 始终存在，无需登录。首版默认提供一个持久本地 Profile，暂不向用户开放复杂的多 Profile 管理。扩展启用、配置、资源授权、本地数据和本地消息以 Profile 为基础。
2. 平台登录与扩展业务登录是可选、独立的会话。未登录平台也可运行本地扩展，或独立登录 PM 等业务服务；所需模型服务或业务服务的认证仍各自生效。
3. 平台登录、退出或切换不自动迁移、清空或切换本地 Profile，也不停止全部扩展后台。退出仅停止依赖该账号的能力；扩展独立业务会话可以保留，依赖平台身份的授权随平台退出失效。
4. 消息范围分别为 Profile + 扩展 + local、Profile + 扩展 + accountScope，以及 Profile 下的平台账号范围。账号退出规则仅作用于退出的账号范围，不影响本地消息或其他独立账号。
5. 同一 Profile 的多窗口共享扩展后台。未来显式切换 Profile 时才切换对应配置、授权、数据与后台；本地 Profile 不是操作系统安全账户，可信 Node 扩展的宿主 API 隔离不构成系统级沙箱。共用设备不能仅凭切换云端账号承诺本地数据安全隔离。

参考机制：[VS Code Profiles](https://code.visualstudio.com/docs/configure/profiles)、[Settings Sync](https://code.visualstudio.com/docs/configure/settings-sync) 与 [Authentication API](https://code.visualstudio.com/api/references/vscode-api#authentication)。上述行为是本平台已确认的设计，不意味着直接采用 VS Code 的全部实现。

### 消息账号隔离模型

1. 扩展向宿主登记业务账号，取得绑定该扩展的 accountScope；登记不要求提交业务 Token。
2. 发布消息、执行按钮和回报结果均绑定对应账号范围，宿主检查来源与账号隔离，不能因当前账号切换而将旧执行归属到新账号。
3. 退出账号后隐藏对应消息，停止派发其新操作；已经发出的操作不能被视为已撤销。
4. 重新登录同一账号后恢复历史消息和未结束执行，再查询业务状态；恢复仍遵守用户清除及消息保留规则，不让已清除消息重新出现。
5. 无账号的扩展使用独立的扩展本地范围。
6. 宿主提供隔离，业务账号真实性由扩展与业务服务验证；扩展提交账号 ID 不等于平台认证。稳定账号标识、会话失效和在途回报的具体校验将在详细设计中明确。

### 账号标识与会话规则

1. 在 Profile 内，以扩展 ID、服务标识、租户标识（如有）及稳定用户 ID 确定业务账号；不以昵称或邮箱作为唯一身份依据。同一账号重新登录复用 accountScope。
2. 每次登录建立新的会话标识，退出后旧会话不能继续发布消息或发起操作。
3. 旧会话已发出的操作，其返回结果仅可结算原账号下的原执行记录，不得归入新账号、恢复隐藏消息展示或触发提醒。宿主必须核验原执行关联，具体凭据与会话校验机制待详细设计。

## 3. 消息模型、更新与生命周期

### 数据模型与动作调用原则

1. 阅读、业务处理、有效性、清除状态分别记录，按钮执行状态使用独立执行记录，不用一个 status 混合表达这些维度。
2. eventKey 必填，在用户配置、来源和账号范围内标识同一业务事件并去重；首版每条消息最多两个操作按钮。
3. 已完成、已失效或已撤回的消息不能重新变成待办；业务重新发起时创建新事件、新消息，仍遵守接收偏好。
4. 按钮引用扩展声明的命令，由宿主检查状态和授权、按需激活扩展后，直接调用已注册的处理函数并等待结果；不通过广播 Hook 驱动按钮业务执行。Hook 用于观察，不承担此调用的执行与结果返回。
5. 宿主绑定 messageId、actionId、invocationId、accountScope 和取消信号等调用上下文，不从按钮业务参数采信身份或授权。取消不代表远端业务已撤销。
6. 调用结果控制加载和错误反馈，消息业务状态由扩展显式更新；命令成功不自动将待办标记完成。服务端成功但本地更新前崩溃时，须通过查询恢复，不自动重放业务写入；服务端幂等仍由扩展与其业务服务实现。

### 消息分类

1. 类别分为“通知”和“待处理”，用于用户筛选。
2. 级别分为“普通”“警告”“错误”，用于视觉提示，不绕过静音、拒收或其他提醒偏好。
3. “待处理”是否完成由扩展更新；阅读状态与处理状态独立，已读不自动变成已处理。
4. 项目邀请、风险预警等业务类型由扩展自行定义，平台不写死具体业务枚举。业务类型与平台类别、级别分别表达，不混用。

### 消息字段可变范围

1. 来源、账号范围、eventKey 和首次接收时间不可修改，同一条消息始终代表同一个业务事件。
2. 类别固定，不能将普通通知更新为待处理以制造新待办；待处理完成后通过业务状态表达，不改变类别。
3. 标题、正文、级别、按钮及未过期的有效期可以更新，遵守消息版本、终态、清除和执行状态等约束，不因字段可修改而恢复被禁止的操作。
4. 新账号、新事件或新的待办应发布新消息，并遵守接收与去重规则。

### 消息更新规则

1. 普通内容更新保留原有已读/未读状态，不再次提醒。
2. 已失效或撤回的消息保留记录，禁用操作按钮；保留仍受用户清除和后续清理期限规则约束。
3. 出现新的待办或风险时，由扩展发布新消息，仍须遵守用户的接收与提醒偏好。
4. 拒收期间允许扩展更新或撤回自己已有的消息，但不能增加未读数或触发提醒，避免留下失效的邀请按钮。不能通过更新接口创建新消息来绕过拒收。

### 消息有效期规则

1. expiresAt 可选，由扩展按业务需要提供。
2. 到期后宿主自动将消息标记失效、禁用操作，并从“待处理”筛选中移除。
3. 过期不自动标记已读或清除，历史记录仍受既有保留与用户清除规则管理。
4. 尚未过期时可以修改有效期，并遵守消息 revision 校验；已经过期后不能通过延长有效期恢复待办。
5. 操作执行期间消息过期不代表远端操作被取消；后续结果仍可记录，但消息保持失效，不因成功回报重新启用操作。

### 乱序更新责任划分

1. 宿主消息使用 revision，更新时检查预期版本，防止并发覆盖。
2. 扩展负责识别业务服务事件的新旧顺序，不将迟到事件作为最新业务状态提交。宿主 revision 不代替业务服务的事件版本或顺序判断。
3. 宿主始终阻止已完成、已失效或已撤回的消息恢复为待办，即使提交方持有最新 revision。
4. 版本冲突时，扩展重新读取并判断如何处理，不自动强制覆盖。宿主版本解决并发覆盖，业务事件版本解决旧数据倒灌，两者职责独立。

### 版本划分

1. 内容、按钮、业务状态或有效期变化时，递增消息 revision。
2. 阅读与清除状态由宿主独立维护，不递增消息 revision，避免用户阅读或清除引发扩展内容更新的版本冲突。
3. 即使预期 revision 一致，宿主仍检查清除状态；更新不得使已清除消息重新出现。
4. 动作执行记录维护独立版本，不因进度回报直接递增消息 revision；若回报同时携带消息更新，消息部分仍遵守其自身版本规则，并与执行结果原子提交。

## 4. 列表、阅读与清除

已确认阅读行为：打开消息详情或点击可用的操作按钮时，将该消息标记为已读；仅打开消息列表不自动标记已读。提供“全部已读”操作。阅读状态与业务处理状态独立：点击按钮标记已读不代表业务操作成功，操作失败也不自动恢复为未读；邀请已读后仍可处于等待接受状态。已读状态按前述规则在同一用户配置的多窗口间共享。

### 列表筛选、排序与角标

1. 提供“全部”“未读”“待处理”筛选，并可按消息来源筛选。
2. “待处理”筛选仅展示尚未完成、未失效且未撤回的待办。
3. 默认按宿主首次接收时间倒序排列；普通内容更新不改变排序位置，不将旧消息顶到前面。
4. 消息中心入口角标只显示未读数，不将待处理数量混入其中。计数遵守账号可见性与清除规则。

### 清除消息规则

1. 清除仅影响消息中心，不取消业务任务、不拒绝邀请，也不代表业务操作已完成。
2. 被清除的消息不因扩展更新或同一业务事件的重复推送重新出现。实现须保留必要的去重/清除标记，不能仅删除消息正文；标记的存储与保留策略在详细设计中确定。
3. 新的业务事件仍可产生新消息，遵守用户接收与提醒设置。
4. 首版提供单条清除和“清除已读”，暂不提供一键清除全部未读消息。

### 批量操作边界

1. “清除已读”跳过仍待处理的消息，即尚未完成、未失效且未撤回的待办，避免批量隐藏未完成事项。
2. 用户仍可单条清除这类消息，操作时提示“仅移除消息，不取消待办”。
3. “全部已读”和“清除已读”均作用于当前筛选范围，包含所选来源过滤；操作文案显示实际可操作的消息数量。“清除已读”的数量不包含被跳过的待处理消息。

## 5. 动作注册、派发与状态机

### 动作执行机制

1. 通过 extension.json 贡献点声明命令和参数契约，扩展激活时注册处理函数。消息 action 仅引用已声明命令及业务参数，不接受任意函数名、脚本或执行 URL；复用现有命令与 Operation 路由。
2. 调用经扩展进程通道异步执行，不在 UI 线程执行扩展代码。点击立即显示反馈，页面保持可操作；同一消息的业务按钮在执行中禁用，状态由多窗口共享宿主协调，防止互斥操作同时提交。
3. 调用采用有界等待，具体时限与现有 Operation 策略统一。超时后宿主结束等待并发出取消信号，但不据此认定远端操作失败或已撤销，不自动重试业务写入。
4. 长任务尽快返回“已受理”（可关联业务服务任务 ID），宿主停止按钮加载但不自动完成待办；扩展通过自己的服务推送或查询更新后续状态，业务任务由扩展维护。
5. 宿主限制并发与排队数量；已经超时但实际仍在执行的处理函数不能被视作已释放执行容量。对同步阻塞采用进程健康检测，必要时终止扩展进程；终止不能保证撤销远端副作用。
6. 动作结果区分“已完成”“已受理”“明确失败”“结果未知”。消息业务状态仍由扩展显式更新；请求可能已生效但无法确认时使用“结果未知”，不能误报明确失败。

### 按钮点击校验规则

1. 页面点击提交消息 ID、动作 ID 和展示时的消息 revision。
2. 宿主读取当前记录，检查消息版本、有效性、账号、资源授权及执行状态；不能只依赖页面的按钮状态。
3. 消息版本发生变化时拒绝旧点击，提示“消息已更新，请重新操作”。首版严格校验整条消息 revision，即使仅正文变化，也须刷新后重新点击。
4. 执行命令及业务参数取自宿主持久化的消息，不能采信页面传入的替代命令或参数，避免展示与实际执行不一致。

### 在途操作与按钮更新规则

1. 动作派发时，宿主保存命令、业务参数及消息 revision 的执行快照。
2. 后续消息更新不改变已派发操作的命令、参数或原执行关联。
3. 修改或删除按钮不能解除该消息的重复提交限制，不能通过替换按钮绕过“执行中”“处理中”或“结果未知”的约束。
4. 执行结果始终关联原 invocationId；回报附带消息更新时，仍须校验当前消息版本，并遵守已确认的原子提交与冲突处理规则。

### 动作分类与处理中可用操作

1. 动作区分“业务提交”和“查看／查询”，分类在贡献点声明，不能由消息临时指定或覆盖；具体声明字段待契约设计。
2. 同一消息存在未结束的业务提交时，禁止再次发起业务提交，包括“接受／拒绝”等互斥操作。
3. 查看详情、查询进度仍可使用，但必须遵守授权、消息版本、有效性及限流规则；该例外仅针对业务提交占用，不放宽失效或撤回消息的按钮禁用规则。
4. 查看／查询不得执行接受邀请、删除数据等业务写入。宿主按操作契约约束，可信 Node 扩展仍由开发者负责正确实现，分类不构成对任意 Node 副作用的系统级隔离。

### 扩展更新后的历史消息兼容规则

1. 更新扩展不删除历史消息，历史仍遵守既有清除和保留规则。
2. 点击旧消息时，宿主按当前安装版本重新检查命令是否存在、参数是否符合当前契约。
3. 命令被移除或参数不兼容时禁用对应操作，并提示“当前扩展版本不支持此操作”。
4. 宿主不自动替换命令或转换参数；扩展需要支持历史消息时，应保留兼容处理逻辑。

### 消息按钮执行反馈

1. 执行中显示加载状态，阻止重复点击；防重复提交须由共享宿主协调，不能只依赖单窗口按钮禁用。
2. 业务成功后由扩展更新消息，例如“邀请已接受”；宿主不因点击或命令已派发就认定业务成功。
3. 失败时显示原因并保留消息，已读状态不回退。
4. 结果未知时明确展示该状态，不自动重试原业务操作；先由扩展查询业务状态，避免重复提交。无法查询或仍无法确认时保持结果未知，不能将其当作确定失败。查询接口、恢复流程及跨窗口执行状态的持久化细节在详细设计中确定。

### 按钮恢复规则

1. 已完成：依据扩展更新后的消息展示操作；不能仅因函数返回就重新启用尚未核对业务状态的提交按钮。
2. 已受理：停止按钮加载，显示“处理中”，禁止重复提交；允许查看进度。
3. 明确失败：对仍有效、可重试的操作允许用户再次点击；重新执行仍须检查消息状态和授权。
4. 结果未知：禁止重复提交，允许查询状态或进入扩展页面核对；不能把查询入口当成再次提交原业务操作。
5. “处理中”和“结果未知”跨窗口共享，并在应用重启后保留。扩展报告后续业务结果，由宿主更新执行记录；刷新页面或重新启动不能解除提交限制。后续反馈接口及消息业务状态与执行记录的一致性，在详细设计中确定。

### 动作执行状态流转

| 当前状态 | 允许的后续状态 |
| --- | --- |
| 执行中 | 已完成、已受理、明确失败、结果未知；仅在确定尚未派发时可进入未执行 |
| 已受理（处理中） | 已完成、明确失败、结果未知 |
| 结果未知 | 查询确认后进入已受理、已完成或明确失败 |
| 已完成、明确失败、未执行 | 本次执行结束，不再修改结果 |

明确失败或未执行后，用户重新点击创建新的 invocationId，原执行记录保留，且仍须满足消息有效性、授权与可重试条件。重复回报同一结果按既有幂等规则处理，不构成新的状态流转。执行“已完成”不自动代表消息待办完成，消息业务状态仍由扩展显式更新；结果未知不能未经业务核实直接转为明确失败或释放重复提交限制。

### 派发前故障边界

1. 用户点击后，宿主先持久化执行记录、占用消息的业务提交位置，再调用扩展；持久化失败不得派发。
2. 确定尚未派发时发生取消或校验失败，可记录“未执行”终态并释放本次提交限制。它与“业务明确失败”分开记录，表示原业务调用尚未派发。
3. 一旦进入可能已派发的阶段，崩溃或超时后无法确认结果时进入“结果未知”，不能当作未执行。具体派发阶段标记与崩溃恢复判据须在存储设计中明确。
4. “未执行”由宿主根据派发证据判定，不能仅凭超时、断连或未收到响应推断远端没有产生影响。

## 6. 结果回报、幂等与恢复

### 后续结果回报职责（接口暂名 messages.reportActionResult，签名未冻结）

1. 扩展按 invocationId 回报后续 outcome，并可附带 messageUpdate。宿主核验来源与账号范围，仅允许更新该扩展在对应账号下的执行记录。
2. 执行结果与本次附带的消息更新在宿主本地一起提交，避免出现结果已成功而消息更新未落盘的部分提交。这不构成与远端业务服务的分布式事务。
3. 相同结果重复回报不重复应用更新、不产生额外提醒；冲突结果明确拒绝，不覆盖已经确定的结果。具体幂等比较与版本冲突规则待接口细化。
4. 消息已被用户清除时仍可记录执行结果，但不得恢复消息展示。
5. 不提供客户端自行解锁按钮的接口。处理中或结果未知时，扩展须依据业务查询、服务推送等取得的结果回报；不能通过直接启用按钮绕过执行状态约束。

### 结果回报的版本冲突与幂等规则

1. 同时包含执行结果与消息更新的回报必须全部成功或全部不提交。消息版本冲突时明确返回冲突，保留原执行状态，不提前解锁按钮。
2. 扩展重新读取并判断后，仅重试结果回报，不重新执行远端业务操作。
3. invocationId 标识一次按钮执行，reportId 标识一次结果回报。同一 reportId 和相同回报内容在提交成功后重试，返回原已提交结果，不重复应用更新；同一 reportId 携带不同内容则拒绝。修改回报内容后使用新的 reportId。
4. 幂等识别必须覆盖提交成功但响应丢失的情况：相同回报的成功重试不得因其原预期版本已过期而误报版本冲突。幂等记录与本地结果在同一事务中提交，记录作用域绑定原来源、账号和执行。

### 应用重启后的动作恢复机制

1. 宿主持久保留未结束的执行记录；扩展激活后可查询自己当前账号范围内“处理中”或“结果未知”的执行。
2. 恢复记录提供 invocationId、消息 ID、动作 ID，以及扩展此前返回且已保存的业务任务 ID（如有）。
3. 扩展查询业务服务后通过 reportActionResult 回报结果；宿主不重新执行原按钮命令。
4. 无法查询确认时保留“结果未知”，允许用户进入扩展页面核对，不自动解除提交限制。
5. 业务请求可能已经发出，但业务任务 ID 尚未本地保存就发生崩溃。建议扩展使用 invocationId 作为服务端幂等与查询关联标识；服务端不支持时，平台不能保证自动恢复或远端业务恰好执行一次。

## 8. 字段与 SDK 草案（尚未冻结）

本节将讨论过的字段和方法集中列出，便于下一轮契约评审。已确认的是前述行为约束，不是下列所有字段名、枚举编码、方法签名或错误返回结构；本节不修改现有 M1 SDK。

### 8.1 数据模型字段映射

| 对象 | 字段草案 | 责任与约束 |
| --- | --- | --- |
| 消息身份 | id、profileId、source、accountScope、eventKey | 宿主生成 ID、绑定来源与范围；扩展提供必填 eventKey；去重范围为 Profile + 来源 + 账号范围 + eventKey |
| 消息内容 | title、body、category、severity、businessType、actions | 纯文本、固定类别、最多两个按钮；业务类型由扩展定义 |
| 消息版本与时间 | revision、receivedAt、updatedAt、expiresAt、occurredAt（可选提案） | 宿主维护内容版本与接收时间；业务发生时间不作为置顶手段 |
| 阅读与清除 | readAt、dismissedAt | 宿主维护，独立于内容版本；不代表业务完成或取消 |
| 业务状态 | pending / resolved，普通通知不适用 | 编码待评审；已确认与阅读、有效性分离 |
| 有效状态 | active / expired / withdrawn | 编码待评审；过期与撤回禁用按钮，不能恢复待办 |
| 动作引用 | actionId、label、commandId、arguments | 命令及分类来自贡献声明，参数须符合契约，不携带凭据 |
| 执行记录 | invocationId、消息与动作 ID、账号与会话关联、执行快照、执行状态、独立版本、业务任务 ID（如有） | 宿主保存与校验；后台恢复不可重放原业务操作 |
| 回报记录 | reportId、invocationId、回报内容或可比较表示、提交结果 | 与本次结果原子持久化；同 ID 不同内容拒绝 |
| 去重与清除记录 | 来源/账号范围、eventKey、清除或拒收处理信息 | 具体结构与保留期限待定，不能仅靠删除正文实现清除语义 |

分类编码可采用 notice / actionRequired，级别编码可采用 info / warning / error；这是命名提案，不是已发布枚举。类别、阅读、业务处理、有效性、清除、执行状态不得混为单一 status。

### 8.2 消息 SDK 职责清单

| 方法草案 | 职责 | 评审状态 |
| --- | --- | --- |
| publish(input) | 发布消息并按 eventKey 去重 | 发布与去重原则已确认；重复发布的精确返回值待评审 |
| getByEventKey(eventKey) | 读取自身账号范围内的消息和版本 | 方法与可读字段范围待评审 |
| update(id, patch, expectedRevision) | 按版本更新内容或业务状态 | 版本及更新约束已确认，签名待评审 |
| withdraw(id, expectedRevision) | 撤回自身消息 | 撤回行为已确认，签名待评审 |
| getPreferences() | 查询来源的接收与提醒偏好 | 接口待评审；宿主每次发布仍检查最新偏好 |
| reportActionResult(...) | 回报后续结果，可原子附带消息更新 | 职责、reportId 幂等与冲突规则已确认，签名待评审 |
| 未结束执行查询（方法名待定） | 获取当前账号范围内待恢复执行 | 恢复职责已确认，分页与字段待评审 |
| 账号登记、会话建立/退出（方法名待定） | 建立受宿主管理的账号与会话上下文 | 隔离原则已确认，句柄和在途回报校验待评审 |

讨论中的建议是由 Node 后台调用消息 API，页面通过声明的命令进入后台。拒收作为正常业务返回、重复 publish 不覆盖原内容、查询不暴露阅读追踪数据等具体 API 细节仍需集中评审，不以本次文档整理视为全部批准。

结果回报输入至少需要表达 invocationId、reportId、outcome，以及可选 messageUpdate 和其预期消息版本；执行记录独立版本如何传入、返回何种冲突信息仍待定义。未执行是宿主判据，不能由扩展随意宣称来解除未知执行的限制。
