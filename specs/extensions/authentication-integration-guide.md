# 扩展与业务服务认证接入指南（预备稿）

> 2026-10-08 实现更新：消息操作与扩展企业认证已有源码预览链路。当前可调用接口与明确限制以 [消息按钮与认证接入规范](message-actions-auth-guide.md) 为准。以下设计中的账号选择器、账号消息与其他未来能力不代表本次已实现。

状态：企业 OIDC、资源声明和 SDK 首版已开放源码预览，可复制接口见 [现行接入规范](message-actions-auth-guide.md)。以下内容同时保留服务端职责及未来多账号目标，不代表全部已实现。

## 1. 选择接入方式

| 服务情况 | 接入方向 |
| --- | --- |
| 纯本地功能 | 不声明不必要的认证要求，无需平台登录 |
| 接受已配置企业身份的业务 API | 申请对应账号、目标 API 和权限范围的授权，由服务器校验授权并进行业务鉴权 |
| 独立公司的账号服务 | 配置该服务的认证连接；不自动获取或使用其他公司身份 |
| 已建立身份联合的服务 | 明确受信任 issuer、目标服务及账号映射；共享浏览器会话不等于共享任意访问令牌 |
| 使用 API Token 的服务 | 独立的凭据输入与秘密存储流程；不得写入普通配置、聊天或日志 |

“需要认证”通常针对某些业务能力，不要求将整个扩展或本地功能锁在登录后。

## 2. 企业管理员准备什么

采用 OIDC 方案时，需在企业身份提供方登记适合桌面公共客户端的应用，准备 issuer、clientId、允许的 scope、回调登记、租户限制及员工分配规则。客户端注册的维护方需要明确：企业管理员或服务提供商均可负责，平台不会凭一个服务器地址自动获得信任。

建议使用系统浏览器及 Authorization Code + PKCE；不将桌面应用内置 secret 视为可保密凭据。回调 URI 由最终宿主方案与提供方登记共同确定，不由扩展随意指定。[RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)

已确认在“设置 > 账号”提供企业连接列表和新增／编辑表单，支持多条配置、默认连接以及每条配置下多个账号。默认连接仅优先展示，不自动授权；相同 issuer 不会自动合并不同 clientId 的配置。部署导入方式、表单编辑权限、多租户方式与 SAML 网关路径尚未冻结。开发者应记录所需配置，供管理员或有相应配置权限的用户填写。

## 3. 扩展作者提供什么

现行字段是 authentication.resources（id、title、baseUrl、audience、scopes）。以下为扩展作者应表达的业务语义：

- 哪些功能需要连接账号，以及用户可理解的用途说明。
- 受支持的身份提供方/连接配置引用、目标服务和所需权限。
- 请求的最小身份字段；不能以“已登录”为由读取所有账号资料。
- 认证缺失、授权不足、会话失效、用户取消时的行为。
- 本地功能与认证功能的区分，以及账号切换后的数据和连接处理。

推荐交互：后台启动先检查现有授权，不能自动弹登录窗口；用户主动点击“连接账号”后调用宿主选择器。宿主筛选兼容账号，展示扩展和目标服务、请求权限；用户选择已有账号或进入新的登录流程。成功后扩展获得被授权的身份/会话能力，不获得全局账号目录。

业务连接由扩展维护。身份提供方登录会话可复用，但授权适用于哪个服务和是否需要再次验证由授权与服务配置决定。已确认优先提供 SDK 会话管理和宿主代发认证请求，具体接口见 [认证设计](./authentication-design.md)。直接获取访问令牌另行评审，不应预先实现读取平台全局凭据的替代接口。断开扩展连接不等于退出其他扩展共享的登录会话。

## 4. 业务服务器如何建立信任

服务器必须验证面向自身 API 的访问凭据，不能信任客户端提交的姓名、邮箱、userId、accountScope 或“已登录”布尔值。ID Token 用于客户端确认登录身份，不应默认当作业务 API 的通用访问令牌。

对于采用 JWT access token 的服务，按所选授权服务器和令牌配置验证受信任 issuer、签名/算法、目标 audience、有效期及适用权限；若采用 RFC 9068 的 JWT access token profile，还须遵守其类型及验证要求。不能只解码 JWT 而不验证，也不能因为签名有效就接受发给另一个 API 的令牌。[RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html#section-4)

对于非 JWT 访问令牌，应采用提供方支持的验证或 introspection 机制，不假设所有 Token 都可本地解码。最终协议库及验证配置需在实际服务接入时核对。

服务端还须独立完成业务权限检查，例如用户能访问哪个团队、能否接受邀请或提交报销。通过身份认证不代表拥有所有业务权限。账号映射应使用稳定的提供方用户标识和租户边界，不仅凭邮箱自动关联不同企业用户。

## 5. 账号生命周期与消息

- Profile、本地消息范围和业务账号范围独立，平台退出不自动销毁本地扩展数据。
- 使用独立业务认证的扩展不默认跟随平台退出；依赖平台身份的授权随其失效。
- 退出业务账号后停止新派发、隐藏对应消息，旧会话不能继续发布；已发出的调用不能当作已取消。
- 旧调用的结果只能结算原账号的原执行，不得发送到新账号或重新显示隐藏消息。
- 对业务写入建议使用宿主 invocationId 作为服务端幂等/查询关联依据，并提供状态查询，供超时和崩溃恢复；认证本身不保证业务恰好执行一次。

这些规则与 [消息中心设计](./message-center-design.md) 一致；accountScope 只承担本地隔离，服务端不把它作为认证凭据。

## 6. 未来必须交付的开发材料

认证功能发布前，应将本预备稿补齐为经过真实联调的指南，至少包含：

1. 一个受支持企业身份提供方的应用注册步骤，以及完整配置样例。
2. 冻结的认证贡献点 Schema、SDK 类型与账号选择/授权/退出示例。
3. 最小业务 API 示例：验证访问凭据、租户/业务鉴权、错误返回。
4. 本地开发回调与正式 Windows/macOS/Linux 回调配置说明。
5. 多公司扩展隔离、取消连接、会话过期、撤权、错误 audience/issuer、退出后旧推送拒绝的测试步骤。
6. 凭据存储、刷新、日志脱敏、故障诊断，以及明确的版本兼容说明。

在这些材料完成之前，不把仅能登记账号标识的接口宣传成完整认证集成能力。
