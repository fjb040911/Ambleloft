# AmbleLoft 客户端整包差分更新流程 v1

日期：2026-11-04。状态：方案已选定，本文为待实施设计；不代表更新器、CI 或签名已接通。

## 1. 决策与边界

使用现有 AmbleLoft GitHub 仓库的 Releases 发布完整客户端，以 electron-updater 差分下载，校验完整安装包后，在安全排空并重启时安装。宿主与固定版本 Codex 引擎是同一个发布单元；不建设更新服务器，不增加独立引擎仓库或 EngineUpdater。

每个客户端版本绑定一个确定的引擎版本，但宿主升级不要求引擎版本提升。差分复用字节块，不按组件版本跳过下载；缓存、压缩、签名及产物布局影响复用率。差分不可用时允许全量下载。更新不提供进程内热替换，不保证宿主重启期间任务持续执行。

首版支持 macOS 签名 ZIP 更新、Windows NSIS 更新。DMG 和 ZIP 等手动安装产物可继续提供。Linux 首版展示版本及官方下载入口，自动安装另行验收。仅 stable 自动更新；预发布供测试人员手动安装，不进入 stable 候选。

## 2. 架构与职责

```text
GitHub Actions → Draft Release → 产物验证 → 正式 Release
                                               ↓
主进程 UpdateService → electron-updater → 差分/全量下载与校验
          ↓
UpdateCoordinator → 全局派发门禁 → 排空 → 状态保存 → 安装重启
          ↓
启动恢复与健康检查 → 成功 / 恢复界面
```

- UpdateService：版本检查、下载控制、状态广播、错误归类；唯一主进程实例。
- electron-updater：GitHub provider、blockmap 计算、区间下载、缓存、包校验及平台安装。固定经过验证的版本，不自行实现差分算法。
- UpdateCoordinator：跨窗口、跨 profile 的任务派发门禁和更新生命周期；所有入口共用。
- Renderer：显示状态、用户选择和阻塞任务；不直接调用更新器，不接收任意下载 URL 或安装路径。
- 启动恢复模块：读取安装意图、检查实际应用版本、执行数据迁移和健康检查。

## 3. 发布物与版本契约

标签采用 v<客户端版本>，必须与 package.json 一致。所有平台从同一个 commit 和锁文件构建。引擎版本继续由构建配置固定，并核对准备脚本、包锁与引擎 manifest。

每个 Release 包含平台安装包、构建工具生成的 latest*.yml、对应 blockmap、发布说明。不得手写 blockmap 或修改生成后的安装包。增加 release-info.json 供诊断和 CI 审核，包含客户端版本、commit、Codex 版本、构建工具版本、平台/架构、数据库迁移说明、支持的升级基线、产物摘要；它不作为绕过更新器验证的执行指令。

平台元数据必须合并生成或经验证正确汇总，避免多个架构的 CI 作业互相覆盖 latest-mac.yml。实际资产命名与元数据内容以锁定版本的构建工具输出为准。

构建签名证书与 GitHub 发布凭据仅保存在受保护的 CI 环境。公开客户端不内置 GitHub token。保持应用标识、签名身份和安装路径连续，签名轮换须单独验证。生产 macOS 包完成签名、公证；Windows 配置并验证预期发布者签名。

## 4. 维护者发布流程

1. 提交待发布代码，更新客户端版本与 release notes，声明引擎是否改变、数据迁移和升级限制。
2. CI 使用锁文件安装依赖，核对固定引擎来源、资源完整性及许可证。
3. 执行构建、关键回归、引擎协议与历史线程恢复测试。
4. 按平台和架构构建、签名，生成更新元数据和 blockmap。
5. 上传到 Draft Release；分平台上传产物，串行汇总元数据，防止同名覆盖。
6. 从上一发行版执行真实安装升级验证：宿主单独变化、引擎变化、跨版本升级；验证签名、摘要、下载字节和业务状态。
7. 在正式发布前核对全部引用资产齐全、签名有效、平台元数据无覆盖错误。Draft 验证不能替代公开 GitHub provider 验证；首轮用测试仓库/测试发行链路完成公开下载冒烟。
8. 将 Draft 转为正式 Release，并明确设置正确的 latest 版本；用户端下一次检查后发现更新。
9. 监测维护者测试设备与社区反馈。有严重问题时撤下故障 Release，发布更高版本修复；撤下发布不能收回客户端已缓存的安装包。

已经发布的版本不覆盖替换资产。旧版本安装包与 blockmap 至少覆盖支持的升级窗口，首版不主动清理历史 Release。跨版本全量回退也是受支持路径。

## 5. 客户端检查与下载

默认启动稳定 60 秒后检查，之后每 6 小时检查并附加随机抖动；设置页可手动检查。检查失败退避重试，不弹出阻塞对话框，不影响任务。版本检查串行合并；离线、限流与无新版本是不同状态。

默认自动检查、用户点击下载；用户可开启“自动下载更新”，但不能由此推导自动安装许可。自动检查设置可关闭。开发模式不运行生产更新流程。

发现更新后展示当前/目标版本、发布说明、平台及下载状态。引擎版本可从构建信息展示；未知的远端字段不猜测。更新器对比 blockmap，从旧包缓存复制匹配块，通过 HTTP Range 下载剩余区间，重建完整的新安装包，再执行完整性及适用的签名校验。

差分不可用或失败时由锁定版本更新器执行受支持的全量回退；取消必须保持取消，不能作为失败自动重下。认证/签名校验失败不得绕过验证安装。界面显示“正在下载完整更新包”而非承诺固定节省比例。

下载期间正常执行任务。预先检查可用磁盘空间，考虑旧缓存、新包、暂存和安装开销；具体上界按平台测试确定，不仅检查网络下载量。断点续传仅在所选库实测支持时承诺；否则允许重新下载。

下载完成只进入 ready。关闭页面不取消下载；关闭应用不代表允许安装。禁用退出即自动安装行为，只有协调器授权的安装路径才能触发更新器安装，并验证平台行为符合该约束。

## 6. 状态机

```text
idle → checking → available → downloading → verifying → ready
          └→ idle / check-failed           └→ download-failed
ready → waiting-for-idle → draining → saving → installing
                               ↓                ↓
                         ready / blocked     下次启动
                                                ↓
                                  validating → healthy / recovery-required
```

- check-failed/download-failed：当前应用正常工作，用户可重试。
- waiting-for-idle：已选择空闲时更新，仍可正常使用；仅检测空闲，不长期冻结调度。
- draining：原子关闭派发门禁并再次检查活动执行，消除“检查空闲后又启动任务”的竞态。
- blocked：显示具体任务、审批或未保存资源；允许取消本次安装并重新开放门禁。
- saving：刷盘、保存恢复记录；任一步失败均不继续安装。
- installing：进入平台安装器，不再接受新任务。失败恢复行为由实际进程和安装器状态决定。
- recovery-required：不启动后台自动化，提供诊断及修复入口。

建议安装前等待上限为 10 分钟；到期推迟更新，不杀进程。用户主动停止任务仍走现有停止流程，并确认安全边界后才安装。

## 7. 全局安全排空

“立即重启更新”仍必须排空；“空闲时更新”许可仅绑定当前目标版本，可撤销，不自动用于后续版本。仅在应用仍运行时有效；应用重启后重新确认，避免突然再次退出。

门禁覆盖所有窗口/profile，以及聊天、自动化、Workforce、讨论、原生子 Agent、扩展触发和输入 outbox 派发。阻止新执行，但必须允许当前执行所需的回执、审批响应、工具结果与结束清理继续处理。

排空检查包含：运行中 turn/子任务、RPC、工具与扩展操作、等待审批、发送结果未知的提交、数据库写入、表单/编辑器草稿、终端进程和 SSH 活动。用户编辑导致状态重新变脏时重做保存检查；在最终保存阶段禁止产生新业务写入。

长驻连接本身不必无限阻塞，但有活动工作或未保存状态必须阻塞。未知提交结果禁止自动重放；需要核实或人工处理。等待审批可由用户完成或取消，不能视为普通空闲。

新输入在门禁期明确提示稍后重试，或使用已存在且已验证的持久队列；不得为了更新临时引入内存队列。自动化触发按现有持久调度策略延后，不重复生成任务。

现有 before-quit 必须拆分为“可取消的准备阶段”和“不可逆关闭阶段”。准备失败不能提前关闭终端、SSH、扩展和数据库。完成门禁、排空及保存后才调用有序 shutdown，并在成功关闭后交接安装器。普通退出与更新退出共享基础关闭逻辑，但使用明确退出原因，防止递归或重复安装。

## 8. 持久化与启动恢复

在应用数据目录的 updates/transaction.json 原子记录：schemaVersion、目标/来源应用版本、事务 ID、状态、开始时间、最后错误；不记录密钥、对话内容或可由 UI 注入的安装路径。下载缓存由更新器管理，不重复发明缓存协议。

每个不可逆阶段前持久化状态；成功回执后更新状态。重启恢复以实际运行版本和重新验证的文件为依据，不把 transaction 中的 installing 当成已成功。

新版启动顺序：

1. 获取单实例锁，读取上次更新意图，暂缓后台任务派发。
2. 检查应用版本、内置引擎 manifest 和可执行版本。
3. 以一致性方式备份待迁移数据；SQLite 使用支持的备份方式或关闭写入后处理，不能仅复制正在写入的主文件而忽略 WAL。
4. 执行事务化、可重复检测的数据迁移，失败进入恢复界面。
5. 验证数据库、配置、引擎隔离握手、核心服务及 IPC；健康检查不调用付费模型、不执行用户业务。
6. 标记 healthy，恢复窗口及草稿，开放派发。中断/未知结果任务保持待核实，不能因为启动恢复自动重发；已持久排队且满足现有幂等契约的任务按正常规则继续。

引擎真实 codex-home 的兼容性必须在发布前用历史会话样本验证，不能用临时 home 预检代替。首次写入前备份用于人工恢复，不承诺任意引擎格式升级可自动回退。

新应用已经产生数据后，禁止直接恢复旧备份覆盖新增写入。首版不做任意版本自动降级；优先发布更高版本修复。手动旧版安装仅在数据兼容性确认后进行，并保留现场备份。

## 9. UI、IPC 与诊断

设置页“版本与更新”：当前客户端/引擎版本、检查时间、更新说明、下载进度、状态、阻塞原因；提供检查、下载、取消下载、立即重启更新、空闲时更新、取消计划和稍后处理。

建议 IPC：update:getState、update:check、update:download、update:cancelDownload、update:scheduleInstall、update:cancelInstall、update:event。授权绑定可信窗口/profile；安装请求绑定目标版本及状态 revision，过期请求拒绝。所有窗口共享主进程状态，不各自发起更新。

本地结构化日志记录版本、平台、阶段、耗时、差分/全量结果、实际下载字节及错误类别；不采集业务内容。首版不增加默认远程遥测，用户可导出脱敏诊断。若所选库无法准确暴露差分网络字节，验收使用下载代理/网络测量，不把重建进度误当网络流量。

## 10. 验收矩阵

| 场景 | 必须结果 |
|---|---|
| 首次安装 | 内置引擎直接可用，无额外引擎下载 |
| 只改宿主、引擎不变 | 使用连续真实产物验证差分；记录网络字节、复用效果，不宣称零引擎字节 |
| 引擎升级 | 完整组合通过协议与历史线程恢复测试 |
| 无旧缓存/旧 blockmap 不可用 | 安全全量下载并成功安装 |
| 网络中断/Range 不可用/限流 | 重试或全量回退，当前任务不受影响 |
| 下载取消 | 不触发回退下载或安装 |
| 摘要/签名错误 | 拒绝安装，保留当前可用版本 |
| 磁盘不足 | 清晰失败，不损坏当前安装及用户数据 |
| 多窗口与后台触发竞态 | 关门后无新任务进入，当前任务能收尾 |
| 审批/工具运行/未知提交 | 阻塞安装，不强杀、不重放 |
| 保存失败 | 不调用安装器，可取消并恢复使用 |
| ready 时普通退出 | 未授权安装时不安装，逐平台验证 |
| 各事务边界强制结束进程 | 下次启动可判定真实状态，不假成功 |
| 新版迁移/健康检查失败 | 不派发任务，提供恢复诊断 |
| 跨版本与跨架构 | 支持基线到新版可升级；错误架构不可安装 |
| 发布撤回 | 新检查不再推荐；已缓存版本不承诺远程撤销 |

macOS 和 Windows 分别用至少两个签名安装版本完成端到端验证，并保留版本、产物摘要、下载数据量和测试记录。差分节省率先实测，再设性能阈值，不以固定百分比作为未验证承诺。

## 11. 实施阶段

1. 发布基础：接入并锁定 electron-updater，调整 NSIS/macOS 打包、签名及 Draft Release 流水线，验证元数据和安装包。
2. 只读检查与下载：主进程 UpdateService、IPC、设置页、日志；先不启用自动安装。
3. 生命周期协调：全局门禁、阻塞检查、草稿保存、退出重构和安装事务。
4. 启动恢复：数据备份/迁移、健康检查、诊断及后台派发控制。
5. 真实发布验收：连续版本差分、全量回退、故障注入、多窗口和跨版本升级，通过后向社区开放。

当前没有更新器的旧版本需要先手动安装第一个带更新能力的版本，之后才能验证自动升级。首次下载是否可差分取决于平台缓存，必须允许全量路径。
