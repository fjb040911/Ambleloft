## 空间描述

可粘贴到项目空间的目标中：

> 完成一个内部设备维修工单示例：员工通过本地网页登记设备故障、查看工单及处理状态，API 与数据运行在阿里云测试服务器。通过目标澄清、方案审阅、本地与 SSH 项目开发、联调测试、远端部署和验收，验证多专家协作的全过程。主持人根据空间成员的实际职责安排工作，并保留决策、资料和任务结果的来源。全程只使用虚构业务数据。

## 测试前准备

1. 在“团队与项目”保留现有成员和分工，关联本地网页项目与阿里云 SSH 项目。成员应覆盖需求、技术设计、实现、测试及部署能力；名称不必叫“产品经理”或“架构师”，分工和项目授权要清楚。
2. 沿用已经配置的 SSH 连接 `47.116.195.229`。连接认证由宿主管理，提示词、文档和代码中不放密码、密钥。沿用空间实际关联的项目目录，不让模型猜测本地或远端路径。
3. 在讨论输入框确认当前接收者为“主持人”；若此前固定过专家，点击“回到主持人”。新建讨论时不选择专家、不输入 `@`。
4. 需要清理旧试跑时，在讨论列表选中原讨论，点击标题右侧“讨论操作（…）→ 删除讨论…”。有活跃运行时先停止并等待结束。确认后整条讨论及全部后续轮次移除；已保存的文档、任务草稿、协作计划、来源快照和原始专家任务保留。关闭讨论仅结束讨论，可重新打开；删除不可恢复。

## 第一条讨论消息

直接粘贴以下内容。不需要点名角色，也不指定成员发言顺序。

```text
我想做一个内部使用的“设备维修工单”测试项目。

员工在网页上登记设备故障，提交后能查看已有工单和处理状态。第一版先跑通登记、提交、查询和数据持久化；只使用虚构数据，不做登录、权限体系、通知和复杂工单流转。

使用这个空间已关联的项目：网页在本地开发和测试，API 在阿里云 SSH 项目中开发、部署，业务数据放在独立数据目录。测试服务只监听服务器 127.0.0.1，通过 SSH 隧道供本机访问，不修改现有 Store 或其他服务。接口前缀用 /api/v1，服务器端口先用 18765；如果有端口冲突请报告，不直接停止别的服务。

请先和我把必要的业务范围、页面行为、接口约定和验收条件明确下来；缺少关键决定时引导我补充，能给建议的先给建议，需要检查的环境事实不要当成已经验证。

方案明确后，整理出可审阅的协作计划：每项工作写清交付、验收方法、执行项目、负责人和依赖，覆盖本地开发、远端 API、联调测试、部署和最终验收。先完成讨论和计划审阅，由我确认后再启动施工。
```

这里的 `/api/v1` 与 `18765` 延续本案例已有的用户决定。监听方式、目录隔离是目标约束；端口可用、工具已装、隧道已连通仍是待验证事实。

## 怎样判断主持人安排合理

不以是否出现某个角色名、是否固定五个人发言来判定。检查以下行为：

- 主持人先判断信息是否够用；信息充分时可以直接委派，不应为了流程而重复询问已给出的内容。
- 确需你决定的问题集中追问，一次最多三个关键问题；可以用表单，也可以在聊天中补充。
- 需要前置结论的技术方案应读到实际需求结论。独立的环境核查或风险分析可并行，但不能拿尚未确认的假设当成约定。
- 委派说明应能看出“为什么这位专家介入、需要交付什么”，对应空间内真实成员职责。某种能力不足时说明缺口，不虚构新专家。
- 汇总区区分用户决定、待采纳建议、待确认问题和待验证事实，并能回到相关消息或专家贡献。
- 讨论阶段不自动创建施工运行。模型说“可以开始”不等于用户已经批准执行。

深入讨论时正常输入即可，默认仍由主持人接收。只有需要单独追问时才 `@` 一位专家；这只影响当前消息，下一条没有 `@` 的消息回到主持人。要连续直聊，显式使用“继续与此专家讨论”，结束后点“回到主持人”。

## 从讨论到执行

1. 审阅当前方案后点击“整理为任务”。任务草稿固定此刻的讨论和资料来源；讨论之后修改不会偷偷改写已经保存的任务。
2. 在任务整理页面检查信息并补齐缺项。重点核对实际项目、负责人授权、验证方法和依赖。正式需求或架构文档可保存并采纳，但不把“必须先出文档”作为一切任务的门槛。
3. 第一轮推荐形成以下工作包；具体人员由空间成员能力决定，下面不是硬编码的角色流程。

| 工作包 | 预期交付与验证 | 依赖 |
| --- | --- | --- |
| 明确需求与接口 | 最小字段、状态、错误反馈、接口契约和可验证验收条件；用户审阅 | 前置讨论 |
| 本地网页 | 登记表单、提交反馈、查询列表和错误重试；本地构建及组件测试 | 需求与接口确认 |
| 远端 API 与数据 | 创建与查询接口、参数校验、持久化、独立部署配置；API 测试和重启后数据检查 | 需求与接口确认 |
| 联调与测试交付 | 通过 SSH 隧道连接真实测试 API，验证正常、缺项、失败重试和持久化；记录可复现证据 | 网页与 API 验收 |
| 测试环境部署及验收 | 启停、健康检查、日志、回退说明；核对监听地址、服务隔离和完整业务链路 | 联调通过，部署范围确认 |

网页和 API 在不同项目目录且契约明确后可并行。共用远端目录的任务需要串行；后续工作等待上游验收，不能把“运行完成”等同“验收通过”。API 开发期的独立测试服务与最终被验收的部署版本应记录清楚。

4. 先“保存计划”核对分工；准备好后明确“启动计划”或“确认并启动”。SSH 授权、工具执行确认按宿主现有权限流程处理。
5. 在任务详情内查看真实回复、文件或命令证据，再做验收。失败填写原因，返工保留原始执行记录；暂停的计划不会因为验收而自行恢复。
6. 最终通过网页提交一条虚构工单，查询确认，重启独立测试服务后再次查询。关闭 SSH 隧道检查网页错误反馈，重新连接后重试。检查未影响现有 Store，记录版本、命令、测试结果和剩余限制。
