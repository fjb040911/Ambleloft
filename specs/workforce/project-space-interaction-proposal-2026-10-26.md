# 项目空间交互优化方案

日期：2026-10-26
状态：设计评估与建议，尚未实施
方法：Impeccable 的 Shape / Operate；沿用现有 shadcn/ui 组件和已确认的工作平台视觉体系。

## 1. 功能理解与设计目标

协作工作平台的核心是：用户组织多个 AI 员工，围绕目标讨论、形成依据、分工执行，再根据证据验收。它不是人类成员的群聊或邀请管理平台。

| 模块 | 负责什么 | 与项目空间的关系 |
| --- | --- | --- |
| 角色库 | 提供可安装、可复用的角色模板及技能声明 | 员工能力的来源 |
| 我的员工 | 保存个人可复用的员工配置 | 加入空间后另设本空间职责与项目范围 |
| 项目空间 | 承载一个协作目标及其讨论、依据、执行与验收 | 本方案的主要工作界面 |
| 关联项目 | 提供实际工作目录和 Local / SSH / SSH→Docker 执行环境 | 一个空间可关联多个已有项目，不复制仓库，也不要求空间有根目录 |
| 知识与决策 | 查找授权范围内可追溯的历史来源 | 为讨论和任务提供引用，不等于自动加载所有历史记忆 |

当前空间已有完整的五个页签：**概览、讨论、文档与产物、任务、团队与项目**。建议保留，用清楚的跨页衔接串成工作流程。

用户已确认优先目标：“进入空间后，清楚知道进展和下一步”。本版同时覆盖讨论到验收的完整链路。成功标准是用户能够直接回答：现在推进到哪里、什么需要我处理、为什么卡住、处理后会影响什么。

## 2. 当前问题与依据

评估依据为现有 React 实现、产品要求和 2026-10-26 保存的真实流程截图；本轮没有重新运行完整远端执行流程。

| 现状 | 交互问题 | 建议 |
| --- | --- | --- |
| 概览长期展示“先对齐，再一起推进”、数量指标和流程介绍 | 已开始工作的空间仍像欢迎页，待验收、失败和依据更新分散在其他页签 | 将概览改为工作入口；介绍仅用于首次使用或空状态 |
| 详情页同时有面包屑、返回入口、大标题、说明、页签和分区标题 | 首屏用于描述页面的空间过多，任务主体出现在靠下位置 | 收紧页面头部，减少重复导航与标题 |
| 空间卡片主要展示项目、员工、文档数量 | 数量不能说明空间是否需要处理、最近做了什么 | 展示真实活动摘要和待处理事项 |
| 任务计划内再套工作包卡片，详情和操作全部纵向展开 | 长计划扫描困难，主操作远离当前位置 | 紧凑任务列表配详情面板；动作靠近对象 |
| 文档弹窗将关闭、撤回、修订、导出、采纳同时放在底部 | 常用、低频和高影响操作争夺注意力 | 按当前文档状态设置主操作，其余放次级区域或更多菜单 |
| 员工入口写成“与他讨论 / 查看任务” | 一个入口承诺两种结果 | 拆成明确动作，携带员工筛选进入对应页签 |
| 选择空间时重置到概览；从文档跳原始任务会关闭文档 | 用户反复寻找刚才的位置和上下文 | 恢复空间内页签、筛选和滚动位置，并提供来源返回入口 |

## 3. 信息架构与首屏

### 空间列表：让用户选择“要推进的工作”

保留现有列表入口和卡片视觉语言，将卡片内容调整为：

- 名称、简短目标；长名称截断但可查看完整内容。
- 一条最值得关注的状态，例如“2 项待验收”“1 项执行失败”，无待办时显示真实最近活动。
- 当前计划摘要，例如“已验收 3 / 5 项”；没有计划时不显示空进度。
- 员工与关联项目作为次要信息，更多数量折叠，环境信息放在项目提示中。

点击卡片主体进入空间；更多菜单承载配置操作。提供名称搜索和“全部 / 需要处理”筛选。默认按真实工作活动排序，打开或选中空间不改变排序；具体活动包括提交讨论、保存文档版本、任务状态变化和验收。

### 空间详情：稳定框架，突出当前工作

```text
项目空间 / 产品发布                       [更多]
产品发布                 准备新版发布资料与交付

概览  讨论  文档与产物  任务  团队与项目
───────────────────────────────────────────
需要你处理                              查看全部
待验收  发布文案已完成                  [去验收]
执行失败  测试环境连接失败              [查看原因]
依据更新  新版方案影响 2 项工作         [检查影响]

当前计划                                查看任务
发布准备    已验收 3 / 5 项
下一项：完成文案验收后，解锁发布包整理

当前依据                                查看文档
发布方案 v2 · 已采纳      v3 草稿待审阅

最近动态
文案员工完成了发布文案 · 12 分钟前
```

示例中的名称、数量和时间仅用于说明布局，实际界面必须来源于真实记录。

“需要你处理”只纳入用户可以采取动作的事项：待验收、失败或中断、需重新确认的依据变化。等待前置验收的任务在当前计划中解释原因，不把每个等待任务都变成一条告警。每条事项直接进入目标对象及其上下文，避免只跳到页签首页。

不展示根据任务数量推测的总百分比；使用“已验收 / 总项数”和具体状态。多个计划时按需要处理的程度排列，可切换查看其他计划。

没有待处理事项时，简短显示“暂无需要处理的事项”，将当前计划前移。首次创建空间时，才出现轻量引导：添加员工、关联项目、开始讨论；不要求一次完成所有配置。需要写入项目的动作在执行前再说明缺少的项目或权限。

## 4. 五个页签的具体优化

### 概览：工作入口

优先级为“需要处理 → 当前计划 → 当前依据 → 最近动态”。团队和项目用轻量摘要或进入配置的链接呈现，避免再堆一排统计卡。宽屏可将依据放在次栏，窄屏按上述顺序堆叠。

### 讨论：先表达问题，再选择参与者和依据

主区域保留讨论记录与输入框。输入框外侧提供紧凑的“参与员工”“参考资料”“历史范围”摘要，点击后再展开选择器；不要默认把所有员工或历史都加入。

- 选择员工后显示本次参与者，支持按成员查看回复状态；个别失败时只重试该成员。
- 参考资料明确写出版本及“草稿 / 已采纳”，不能只显示文档名。
- 继续讨论保留上轮上下文，并允许调整本轮参与者和引用。
- 提交后立即显示已提交内容及各员工的等待、运行、完成或失败状态。
- 人数、资料数达到当前上限时，就地解释原因与处理方法，不能只让发送按钮失效。
- 结果区提供“整理为文档”，先生成可编辑草稿，由用户检查后采纳。

**能力边界：**当前“收集结果”主要拼接成员回复，不能宣称已经自动提炼共识。若增加“共同结论 / 分歧 / 待确认事项”的模型辅助整理，需要新增能力，并保留来源引用和人工确认。

### 文档与产物：明确“最新”与“正在使用”的区别

列表分开呈现标题、已采纳版本、最新草稿、来源及更新时间。例如“正在使用 v2；v3 草稿待审阅”，不使用一个状态覆盖两种事实。

打开文档默认进入阅读视图，标题下显示来源、版本和使用状态；修订是明确的主动操作。

- 草稿：主操作“采纳此版本”，次操作“继续编辑”。
- 已采纳版本：主操作“创建任务计划”或“查看关联任务”，按实际关联状态决定；修订为次操作。
- 导出、历史版本放工具区；撤回放更多菜单，并解释实际影响。
- 采纳新版本前，展示将受影响的任务及需要重新确认的内容。无依赖时保持轻量。
- 保存草稿不替换已采纳版本；正在运行的任务保留原固定输入，不能静默改用新版。

版本对比和准确的影响清单是建议增加的能力，需要相应查询与数据支持，不能由界面猜测。正文内文件引用、独立产物、代码变更汇总应按用途区分，同一输出位置不重复渲染同一文件。

### 任务：扫描状态、查看证据、推进依赖

计划头保留目标、真实验收进度和计划级控制。工作包改成紧凑列表，每行展示名称、负责人、项目、状态及一条阻塞原因；点击后在详情面板展开说明、固定输入、验收条件、执行记录与证据。

默认按需处理、执行中、等待、已验收分组，同时允许查看依赖关系。单纯看板无法充分表达前置验收要求，不作为唯一主视图。

计划编辑器采用“计划信息 → 编辑工作包 → 检查并保存”的组织方式，默认仅展开当前工作包。保存计划和启动执行是两个明确动作；启动前集中指出缺失负责人、项目或依据等问题。

验收面板先呈现验收条件和实际证据，再给出通过或退回操作，并说明通过后会解锁哪些任务。查看完整原始任务后能回到原验收位置。执行完成显示“待验收”，只有验收通过才允许释放依赖。

暂停、停止、重试等操作使用服务端的真实状态语义；失败原因和可恢复操作放在一起。依据过期需要重新确认，不能通过重试按钮悄悄跳过。

### 团队与项目：低频配置与清楚的责任边界

沿用现有分开的员工和项目编辑流程。列表展示员工的本空间职责、负责项目和当前任务，不复制整个员工档案。分别提供“发起讨论”和“查看任务”。

项目展示名称、环境类型和工作路径；SSH 项目可查看连接名称、主机、端口、远端路径，容器项目再展示容器标识。状态与长名称分区布局，不挤占名称；不展示密码等凭据。只有取得真实连接状态时才显示“已连接”，不能根据保存过连接就推断在线。

## 5. 连续性、视觉与边界状态

- 保存每个空间的当前页签、筛选和滚动位置；通过“待验收”等明确入口进入时，优先使用入口携带的目标。草稿已有持久化能力，应继续保留。
- 跨页签传递对象：讨论转文档保留来源；文档转计划带固定版本；任务回看讨论和原始运行时提供返回入口。
- 统一反馈：提交中立即反馈、失败保留输入、重复点击不重复提交；加载占位与真实空状态分开。
- 首屏降低大标题、重复导航及介绍占比。减少任务区层层套卡，使用分隔线和间距建立层级。
- 沿用现有系统字体、语义圆角、黑白主操作和已确认的淡紫引导风格；淡紫说明仅在有指导价值时出现。状态同时使用文字或图标，不仅靠颜色。
- 使用现有 Tabs、Button、Badge、Tooltip、Popover、Dialog、Sheet 和菜单等组件按职责组合，不另造一套视觉控件。
- 宽屏详情面板保留列表上下文；窄屏转单面板阅读，通过返回按钮恢复原列表。长标题、路径、多个项目必须可截断并查看完整信息。
- 键盘能够到达主要操作；面板关闭后恢复触发点焦点。小屏或缩放时，主要按钮不被遮挡，避免嵌套横向滚动。
- 历史记录、依据缺失、员工删除、权限不足、项目断连分别说明原因和下一步，不统一显示“暂无数据”。

## 6. 实施顺序与能力依赖

| 阶段 | 改动 | 技术边界 |
| --- | --- | --- |
| P0：先让工作可见 | 收紧头部；概览待处理和当前计划；空状态分流；员工动作拆分；页签与滚动恢复 | 大部分可基于已有记录聚合；需核验全部状态映射，不以空间访问更新时间代替工作活动 |
| P1：打通推进链路 | 讨论引用摘要；文档双版本状态；任务紧凑列表与详情；证据优先的验收；跨对象返回 | 涉及页面状态和跨视图入口；精确影响预览、版本对比需新增支持 |
| P2：规模化与辅助能力 | 空间搜索筛选、服务端分页和活动聚合；模型辅助讨论整理；大型计划依赖视图 | 当前快照接口不等于分页接口；历史语义检索和远端产物适配另行验收 |

建议先落地 P0，并以已有空间和新建空间各验证一轮，再推进 P1。完整跨仓库 SSH / Docker 执行与验收尚需实测，界面优化不能替代该能力验证。

## 7. 验收场景

1. 已有空间包含待验收和失败任务：进入概览即可识别并直达处理对象，无需逐页查找。
2. 只查看空间和任务：返回列表时不会因为点击访问改变最近工作排序。
3. 讨论中一个员工失败：其他成员回复保留，能够单独重试失败成员，输入与引用不丢失。
4. 文档 v2 已采纳、v3 为草稿：列表和详情均明确当前依据；保存 v3 不替换任务输入。
5. 新版本影响下游任务：采纳前看到真实影响，采纳后相关任务需要重新确认。
6. 任务完成但未验收：后续依赖仍等待；查看证据并通过验收后才释放。
7. 从任务查看原始运行，再返回验收：恢复原空间、页签、对象和滚动位置。
8. 空空间、长名称、多项目、较多员工、长计划以及窄窗口：核心动作清楚可达，无大面积重复说明或层层滚动。
