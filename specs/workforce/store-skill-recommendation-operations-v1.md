# Store 技能维护与专家职责匹配推荐

日期：2026-10-28。状态：**本地分阶段实施中**，具体实现、证据和缺口见[实施记录](implementation-2026-10-28.md)。本文件补充[产品设计](role-skills-product-v1.md)、[架构设计](role-skills-architecture-v1.md)、[实施验收清单](role-skills-delivery-checklist.md)和[专家交互设计](expert-workbuddy-adoption.md)。测试服务、候选脚本或签名发布器的存在不等于完整自动运营链路已上线；本轮没有线上发布或创建定时任务。

同日补充：产品未正式发布，无需为旧客户端设计兼容路径；下文历史兼容要求以此为准。仍须保持当前宿主固定版本及已保存专家、运行任务的选择不被静默替换。

## 1. 用户确认与范围

**Store 定期维护可信技能目录；AI 根据当前专家职责匹配并解释推荐。** 默认推荐不让每个用户的 Agent 实时联网搜索。Store 为所有用户提供统一的真实来源、固定版本、用途、审核和热度信息；个性化建议在用户主动请求时生成。

官方模板的已审核默认技能组合继续按 [2026-10-27 默认规则](role-skills-defaults-2026-10-27.md)初始化，用户可调整；此后的 AI 推荐是额外建议，**不自动替换、恢复已取消项、勾选、安装或授予权限**。自定义专家可以从空集合开始。用户手动搜索全部技能或导入来源的入口保留；未匹配时可主动发起外网查找作为未来可选能力，不作为首版交付或自动回退，结果须核验并由用户决定是否导入，不能冒充 Store 已收录条目。

体验目标：以当前可用快照快速列出目录和官方推荐，AI 匹配以独立加载状态随后补充，不阻塞浏览、手动选择或保存草稿；具体延迟目标待测量，不承诺未经验证的秒数。

## 2. 端到端职责与数据流（SR-01）

1. Store 发布端周期性发现候选、检查来源、整理分类和证据；通过审核后发布签名快照。
2. Agent 验签并获取同一快照下公开技能数据。按公开分类与本地角色字段召回少量候选；无公开分类可先本地搜索公开索引，不向 Store 发送私人自由文本。
3. 用户点击“AI 推荐技能”后，界面展示选定模型服务、将使用的角色字段及候选摘要；仅将当前角色必要字段和公开候选发送至用户选择的模型服务，不携带项目资料、文件路径、聊天、凭据、员工 ID 或安装清单。实际模型服务处理数据的边界遵循用户现有配置，不宣称请求只在本机完成。
4. 模型只从给定候选中返回引用、理由及适配级别；宿主在相同签名快照中重新解析并核验身份、状态与版本，拒绝未知 ID、重复、撤回及篡改字段。不可用或不确定的候选不得伪装成可安装推荐。
5. 界面将推荐与目录信息分开展示；用户选择添加或取消，已有选择保持。最终提交时执行既有固定版本与最新撤回状态校验。职责更新后可提示旧建议基于较早内容，刷新不改变已选项。

数据路径边界：Store 公开 API 仅接收公开 roleId、categoryId 等目录参数；自由职责不写入 Store 请求、日志、遥测或公开快照。模型调用由用户显式触发，提示并选择服务；其数据不因本方案自动授权给 GitHub 或其他第三方搜索服务。

## 3. 推荐理由、匹配度与热度（SR-02）

每个推荐项至少显示名称、用途、来源/作者、适配理由、适配标签、版本与可查看的来源详情；展示适用平台及依赖或运行环境要求，不能把缺失依赖说成已就绪。

- **官方角色理由**：由发布端维护并审核双语内容，绑定 roleId、roleVersion 和精确 release。同一技能在不同角色可有不同理由；描述哪项职责、何种任务及技能能力，区别于通用技能介绍。标记“角色推荐”。
- **AI 个性化理由**：依据用户当前输入和真实候选，在宿主侧生成，标记“AI 根据当前职责推荐”；不写回公共 Store、不冒充官方审核。仅显示受输入上下文和候选证据支持的理由；无依据可不推荐。记录本地输入摘要、快照、模型及请求版本用于过期判断，不记录凭据或额外私人正文到公共日志。
- **适配标签**：首版为“高度匹配 / 可补充”，解释理由，不展示虚构的精确概率或安全分。AI 标签属于建议，不是质量保证；无法合理判断时省略。优先排序相关性及可用性，再使用可信热度作为辅助；稳定身份打破并列。默认组合以签名绑定为准，不能让 AI 排序覆盖用户选择。
- **热度指标**：仅显示有来源的可核实数据，如 GitHub 仓库 Stars；明确标注“仓库 Stars”、仓库地址和采集时间。monorepo 的 Stars 属于整个仓库，不计为某个子目录 Skill 的独立使用量。缺失为 `null`，显示“暂无数据”，不按 0 排名。平台未来如采集真实技能使用量，应单独定义事件、去重范围、时间窗口、隐私口径与防刷规则，未实现前不展示“安装量”。
- **官方精选与审核状态**：清楚区分官方开发、官方审核的第三方来源和用户导入；“精选”表示完成所列审核，不代表安全保证或适合所有环境。校验级别应区分来源核验、打包/安装验证、平台测试与实际任务验证，未进行的验证标记未验证。
- **推荐指数**：首版不发布 0–100 分或星级。后续若确需数值，先定义版本化公式、公开输入、适用对象、缺失值处理和样本证据，经产品验证后再展示；AI 不能自行生成无依据分值。热度和适配度不混称“推荐指数”。

## 4. 技能审核与更新（SR-03）

候选按 `discovered → validated → reviewed → published` 或 `rejected` 流转。每次候选保留来源 URL、仓库和子目录、不可变 commit、发现/采集时间、许可、能力分类、制品摘要、检测与审核结果、审核人/时间、变更原因和证据；模型可以辅助生成说明或分类，但不能自行通过审核、批准发布或执行外部技能内容。

审核至少包括：来源与许可可识别；内容与身份可解析、打包和摘要核对；适用平台及依赖如实记录；角色适配与推荐理由有证据；与默认组合内其他技能的冲突和代表性任务验证按现有发布门槛执行。自动静态检查不能等同于安全保证或跨平台实测。官方模板默认组合仍遵循非空、真实固定版本和组合审核要求；个人自定义技能无需被强制加入默认组合。

对已发布来源定期检查 commit、版本可用性、许可和仓库热度。新内容先形成候选，经过审核后发布新 release；已有版本及摘要不可覆盖。仅热度或排序变化发布新快照；角色绑定、默认组合、双语理由或职责变更按既有角色版本契约发布新 roleVersion。用户已选引用、已保存专家与在途任务快照不随刷新自动变更。

已发现不可用、有重大问题或来源撤销的内容应有 `published / yanked / revoked` 状态及原因。新绑定/安装按既有撤回策略处理；保留可解释的历史记录和旧快照，不静默换成同名技能。采集失败、限流或审核不通过保留上一有效快照并告警；签名状态到期时不能以旧缓存绕过安装校验。

采集频率在各阶段按数据规模、API 配额和运营需要配置，下面的每日/每周只是初始建议，须经运行数据调整，不属于用户指定的固定 SLA。优先条件请求、控制并发、遵循限流和 Retry-After，记录运行状态与上次成功检查点。[GitHub API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)。

## 5. 分阶段实施与验收（SR-04）

| 阶段 | 范围与工作量性质 | 完成条件 |
| --- | --- | --- |
| 第一阶段：小规模人工精选 | 优先沿用现有候选来源、固定制品与签名目录。运营手动选小批真实技能、核验来源、编写角色理由和双语说明；更新使用人工审核发布。维护工作主要是逐项核验与角色组合验证，而非大规模爬虫 | 至少对优先专家形成可追溯真实组合；同一技能在不同角色理由不同；真实来源、安装与选用链路经隔离环境验证；不宣称热度采集或自动更新已上线 |
| 第二阶段：AI 匹配与辅助更新 | 构建本地候选召回、模型选择和提示、结构化输出、未知候选拒绝、停止/过期/缓存；周期检查已收录来源，产生待审核更新；AI 可辅助草拟说明与分类 | 手填专家可生成可解释建议；无模型/离线仍可手工选；审核通过才发布；限流、失败、撤回和旧选择保持通过测试 |
| 第三阶段：扩大发现与运营 | 规模足够时增加新增来源发现、去重、审核队列、运行面板、来源健康与质量抽查；按配额和运营反馈调整频率 | 可观察、可重试、可审计、可回退；新增候选不得自动进入公开目录；人力和运行成本有实际测量 |

阶段顺序表达推荐的实现依赖，不排除用固定协议样例并行开发 UI、Store 和宿主；完成某一阶段须有对应真实证据。是否建设独立运营后台和具体人天，需先盘点现有能力与试运行样本，本文不编造工期或成本。

## 6. 实施接口与一致性（SR-05）

现有 `GET /roles/:roleId/recommendations` 用于官方角色的已审核绑定；`GET /skills` 与签名快照提供公开候选和有据可查的热度字段。扩展字段需版本化并随技能/推荐分片签名，维持中英文投影、来源 ID、快照分页和旧客户端兼容；具体字段与现有 [API 增量契约](role-skills-api-v1.md)联动。

宿主内部命令 `suggestExpertSkills({requestId,draftId,draftRevision,snapshotId?,providerId?,model?,locale?})` 返回绑定请求、草稿版本、签名快照和规则版本的结果；`cancelExpertSkillSuggestion({requestId})` 取消生成；用户逐项采用时通过 `resolveExpertSkillSuggestion({requestId,draftId,draftRevision,snapshotId,listingId,version,locale?})` 再次核验。具体字段与失效语义见 [API 增量契约](role-skills-api-v1.md)。建议结果仅保存在当前宿主进程内，不是可恢复的持久作业。

同一 `requestId` 重试不得产生多个可应用结果；请求与输入摘要、draft revision、snapshotId 绑定。编辑或换模型后旧结果标记过期，用户选择后由宿主校验当前输入和 release；已取消或迟到结果不能应用。生成失败返回可恢复原因，不清空用户输入或已选；返回 `unmatchedCapabilities` 仅做搜索建议，绝不当成技能身份或下载源。

无模型、模型超时、输出不可解析、低置信或候选为空时，显示已审核的官方推荐/目录（如有）与可解释空态，允许手工选择、搜索和导入。Store 离线时可浏览有效缓存并标注时间；安装仍受既有签名/撤回策略限制，不能凭过期缓存伪报成功。明确区分官方角色推荐、AI 个性化建议和用户主动添加来源。
