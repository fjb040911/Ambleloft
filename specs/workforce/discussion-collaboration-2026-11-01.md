# 项目空间多专家讨论分阶段改进

> 2026-11-01 后续决定：主持人协调已获用户批准并实现，最新交互与状态以 [主持人驱动的项目空间讨论](discussion-host-2026-11-01.md) 为准。下文“只实施阶段 1/2”“分别分析为默认”“阶段 3 之后尚未实现”是此前阶段记录，不再作为当前默认规则；旧记录的真实归属与不伪造证据原则继续有效。

本次只实施阶段 1 和阶段 2：记录真实的专家发言身份与上下文来源，让用户能够区分每位专家的输出、执行状态及对应任务。后续先由用户验证，再推进专家互评和协调流程。

## 当前执行事实

选中产品经理与架构师后，宿主分别创建两个运行，分别加载专家配置，并使用各自指定模型或本次默认模型。它们收到本轮用户输入、所选文档和各自在空间内的分工。当前轮的专家不会自动收到另一位专家正在生成的内容。

继续讨论时会提供前轮观点摘录：最多最近 8 轮，直接前轮每位专家取末尾 3000 字符，更早轮次的提示取前 2000 字符、回复取末尾 1000 字符。完整历史仍保留，但不能把摘录描述为完整记忆。

因此当前页面明确称为“分别分析”。“整理为文档”仍为专家原文汇集，不代表协调者提炼或专家已达成一致。用户发起的下一轮可以要求专家核对前轮观点，不能据此声称存在自动互评。

## 分阶段交付与验证门槛

| 阶段 | 交付内容 | 验证通过的条件 |
| --- | --- | --- |
| 1 数据约定与真实归属 | 讨论、用户轮次、专家贡献、执行任务四层关系；稳定贡献 ID；冻结身份与讨论输入版本；兼容旧记录 | 两位专家对应不同贡献与运行；重复提交不重复运行；旧记录不伪造互评与输入快照 |
| 2 可辨识的讨论界面 | 专家姓名和头像、实际模型、独立状态、本轮专家索引、发言依据和完整任务入口；复用现有 Conversation | 同一模型也能区分发言人；长回复滚动仍知道是谁；失败可单独重试；原 Tab 与输入框交互不退化 |
| 3 协调与有限互评 | 协调者决定是否需要跨专家回应；显式记录回复对象与所引用观点；限定轮数、超时、费用预算及停止规则 | 能从真实执行记录追溯“谁回应了谁”；无必要互评时直接结束；禁止为展示而生成虚假交流 |
| 4 信息补充与讨论收敛 | 缺少目标、范围或验收信息时复用声明式表单；协调者整理共识、分歧和待验证项 | 用户能补充而不丢失已有讨论；未解决分歧不被标为已达成结论 |
| 5 文档任务与调度衔接 | 保持讨论 → 文档或证据（可选）→ 任务 → 调度；结论及任务均保留来源 | 结论采纳、任务信息完整性、任务验收和后续自动调度的边界清楚且不重复执行 |
| 6 恢复与综合验证 | 停止、重试、部分失败、重启、旧数据、长讨论、不同模型及中英文端到端验证 | 恢复不重复收费或执行；能够看清缺失和失败；关键流程有回归证据 |

阶段 3 之后尚未实现。未来的 collaboration 模式不得在协调与互评落地之前成为默认模式或可选入口。

## 阶段 1 数据约定

保留现有空间存储及请求接口，新增字段均由宿主生成，不采信模型生成的身份或前端自报的关联。

| 层级 | 数据 | 含义 |
| --- | --- | --- |
| 讨论 | request.discussion | schemaVersion 为 1；id 为首轮请求 ID；mode 当前只有 consultation；provenance 区分 recorded 和 legacy |
| 用户轮次 | request.id、replyTo、round | 每次用户提交生成一轮，关联上一轮；不是某位专家的消息 ID |
| 专家贡献 | participant.contribution | 独立稳定 ID；author 为专家 ID 与当时姓名；stage 为 analysis；当前 replyToContributionId 为 null |
| 执行任务 | participant.runId、contribution.runId | 关联实际 AgentRun；消息、工具、授权与表单继续以该运行作为数据来源 |
| 模型 | contribution.model | 来自实际运行的模型，未记录时为 null；不以当前编辑器选择冒充历史模型 |

contribution.context 记录空间分工、已选文档 ID/标题/版本/hash、实际传入的前轮请求 ID、是否省略更早轮次、允许查询的历史空间 ID。version 为本轮讨论提示、空间目标、分工、文档内容、历史空间范围及前轮观点摘录的 SHA-256 指纹。它描述冻结的**讨论输入**，不是整个模型请求或所有附件/工具调用的指纹；专家角色和技能仍由运行快照保存。

贡献 ID 和 discussion ID 进入运行的 collaboration 关联字段。专家启动失败也保留姓名与贡献 ID；失败不会伪造运行 ID 或模型。模型运行输出不复制进新的贡献记录，避免两份正文漂移。

旧请求在 snapshot 中投影为 legacy，贡献 ID 按请求 ID 与专家 ID 稳定派生，不写回迁移。旧记录的 stage、context 和 replyToContributionId 均为 null。能从原始运行读到的冻结姓名与模型继续显示；缺失信息明确标为未记录。

独立运行不等于隔离了所有外部资源：专家仍使用现有权限与工具边界。本次不改变执行策略、共享资源权限或模型调用次数。

## 阶段 2 展示与交互

1. 讨论标题下用一句说明呈现当前“分别分析”机制。
2. 每轮提供专家姓名与状态索引，点击可定位到该专家的发言并移动键盘焦点。
3. 每位专家的回复有独立的姓名、首字头像、实际模型和状态。头像采用官方 shadcn Base UI Avatar，状态使用已有 Badge。
4. 身份栏随所属回复吸顶，位于空间主 Tab 下方；它在回复结束后随区域退出，不覆盖下一位专家的身份。
5. “依据”浮层呈现本次空间分工、前轮摘录范围、文档版本和讨论输入版本。加载技能移到这里，并说明加载不代表已调用。版本号不再占据主标题。
6. 排队、准备、分析、等待处理、正在停止、已完成、失败和已停止来自真实运行状态。无记录的状态标为未知，不显示虚假进度百分比。
7. 失败且没有正文时显示“本次未产生回复”，不再显示仍在等待；保留原有单专家重新请求入口。
8. 回复正文、工具过程、表单、授权和消息操作继续使用普通任务的 Conversation；发送框继续使用 ChatComposer 与 ComposerControls。没有新增平行聊天实现。
9. 保持全页滚动、主 Tab 吸顶、右侧上下文导航以及底部输入区固定。按原有方式关闭讨论、整理文档、继续讨论及查看完整任务。
10. 本次中英文文案均随应用语言切换；专家姓名和文档内容保留用户原文。

## 用户逐步验证

先完整退出并重新启动开发应用，使 Electron 主进程加载新的数据记录逻辑。仅刷新页面不足以更新宿主。历史讨论仍然可读，但不会因此补出未保存的旧上下文。

1. 打开一个已有讨论，检查专家身份、实际模型、全文入口和“依据”中的历史说明。
2. 新建一轮讨论，选择产品经理和架构师；可以使用同一模型，以检查身份是否仍然清楚。观察每位专家状态独立变化，点击专家索引定位。
3. 上下滚动较长回复，确认专家身份、主 Tab 和底部输入区稳定。切换其他空间 Tab 后返回，验证原有体验。
4. 点击“继续讨论”发送补充问题，检查下一轮“依据”包含前轮观点摘录及原引用版本；这一步依然是用户发起的续轮。
5. 反馈优先回答两点：能否马上判断是谁在说话；能否清楚判断当前是分别分析，而非自动互评。

通过后再进入阶段 3，先确认协调者及互评的可见流程和成本边界，再编码验证。后续每个阶段都按“说明本轮范围 → 实现与测试 → 给出短验证路径 → 根据反馈推进”的方式执行。
