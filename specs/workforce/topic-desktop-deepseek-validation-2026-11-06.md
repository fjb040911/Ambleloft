# DeepSeek 桌面话题任务全流程实测

日期：2026-11-06。结论：发现并修复四处问题，随后通过真实桌面返工、验收、后续调度及同话题第二项任务验证。

## 验证方式与范围

- 使用实际 Electron 应用，通过 Playwright CDP 点击桌面按钮、填写输入框和声明式表单；没有用 IPC 写入任务、伪造模型回复或直接推进状态。
- 独立测试资料目录 `/tmp/topic-desktop-deepseek-20261106`，复用现有 DeepSeek 配置，模型为 `deepseek-flash`。仅预置两位隔离测试专家；空间、讨论、草稿确认、启动、验收、恢复与重试均通过界面操作。
- 测试空间“桌面验收与话题串行 · DeepSeek”，无关联项目。仅使用虚构数据和聊天文本交付，不访问用户项目或远端环境。
- 只读快照用于交叉核验真实状态。脱敏结果及桌面截图见本文末尾，不包含提供商凭据和模型思考内容。

## 实测过程

| 步骤 | 实际操作与结果 |
| --- | --- |
| 讨论引导 | 输入不完整的发布检查目标，DeepSeek 展示原生选择表单；选择“数据报表或分析结论”，确认后继续补充。 |
| 生成第一项任务 | 提供三行虚构网页状态数据，生成两个串行节点：资料整理员出表，验算专家在人工验收后核对。 |
| 确认但不执行 | 点击“确认并保存计划”，状态为待执行，没有执行尝试；随后点击“开始执行”。 |
| 验收与调度 | 核对第一节点表格后通过验收，原页面显示后续节点名称、专家、准备/执行状态及“查看任务”；不必返回流程图。 |
| 完成第一项任务 | 下游真实输出通过 2 项、不通过 1 项、唯一异常 `/api`、不予发布；验收后计划全部完成。 |
| 同话题下一项 | 发现旧实现直接复用历史并生成重复草稿。结束该错误草稿，修复后再次点击“创建下一项任务”；主持人先询问新目标，创建新的空草稿，历史保留。 |
| 生成第二项任务 | 在原话题输入完全不同的 `2+3` 求和目标，生成新任务且不复用网页检查数据；点击“确认并启动”。 |
| 严格检查交付 | 第一节点错误输出计划提案而不是 `5`，因此通过界面提交“未通过”，没有将其算作成功；下游仍等待。 |
| 返工复测 | 修复执行阶段提示，重启隔离应用；从原话题恢复计划、处理任务、点击“核对后重试此任务”。DeepSeek 真实输出单独一行 `5`。 |
| 再次验收与调度 | 验收 `5` 后，同页自动显示后续任务准备、执行、待验收；点击“查看任务”，真实交付为单独一行 `核对通过：2+3=5`，验收通过。 |
| 最终入口与状态 | 返回原讨论，当前任务及右侧话题均为“已结束”，“创建下一项任务”可见；只有一个话题，历史任务 3 项为两项完成计划加一项主动结束的错误草稿。 |

## 本轮修复

1. **执行请求被当成话题**：分析型节点同样使用 `discussion` 模式，仅按模式筛选会把内部执行提示加入话题和对话。通过计划各次执行的 request ID 排除内部请求，保留查看任务证据的入口；覆盖刷新后的恢复路径。
2. **下一项任务重复旧需求**：结束后按钮原先直接打开自动评估，读取整个旧讨论。改为调用已有 `restart-guide` 链路，先收集新目标，再生成草稿；保留历史与用户尚未发送的输入。
3. **验收后仍提示等待上游验收**：依赖已通过时，不再展示缓存的旧等待原因。未满足依赖、计划暂停和资源阻塞仍显示真实原因。
4. **规划阶段与执行阶段混淆**：真实模型将目标里的“准备任务、暂不执行”当作当前执行要求。调度提示明确当前节点已经用户启动，须交付当前工作包；分析任务按指定格式交付，工作任务继续报告变更和验证。内置引导升级至 v7，要求将规划期措辞留在就绪说明中，不写入可执行目标；实际禁止操作、项目与审批约束保留。
