# 员工角色与技能推荐：产品设计 v1

日期：2026-10-26；修订：2026-10-27。状态：待实施设计，非已实现功能或验收报告。

本文由产品经理视角整理本轮讨论。实现契约见[架构设计](role-skills-architecture-v1.md)，交付追踪见[实施与验收清单](role-skills-delivery-checklist.md)。本轮用户决定优先于早期方案；所有流程均复用现有协作工作平台、角色库和全局技能服务。

## 1. 决策来源与旧规范覆盖

### 用户明确要求

- 官方维护角色列表，为角色提供对口的热门技能及推荐理由；Store 定期从 GitHub 收集技能并分类，Agent 展示推荐。
- 2026-10-27 用户补充：角色的主要价值是替不专业的用户选好并默认绑定适合工作的技能，工作时默认带上；只声明分工不足以交付角色价值。
- 保留“导入来源”，技能详情与推荐理由同时可查看。
- 此处不需要用户区分技能是否已经安装。勾选表示员工使用此技能；提交员工配置时检查并自动安装缺少项，导入来源也适用；显示安装过程或真实进度。
- 编辑员工但未修改内容不应该产生草稿。继续收集问题后整体修复；当前任务补齐设计文档，不修改运行代码。

### 本文采用的设计决定

- 保存与准备合并为一次提交；全部所选技能准备好后，原子应用配置。编辑失败保留旧员工版本，新建失败保留待完成草稿。
- 选择器为“角色推荐 / 全部技能”，导入为独立入口；选择器内有临时选择，确认后返回员工表单。
- 后台准备、失败重试、重启恢复、在途任务快照按上一轮讨论补齐成完整流程。
- 无技能员工可提交；技能选择不是必填。新员工默认不自动启动业务任务，不自动加入空间。
- “热门”是发现信号，不等于适合、安全认证或默认强制选择；官方精选与官方开发必须明确区分。
- v1 推荐使用官方维护的角色—技能关系和理由；自定义角色按用户选择的方向/分类匹配，也可主动浏览全部技能。不得为获取推荐默默上传职责、项目或个人员工档案。

### 冲突规则

| 旧条款 | 本轮替代规则 |
|---|---|
| `role-authoring.md` §声明技能要求显示全局已安装/激活时安装；§来源选择器为已有技能/技能库/导入 | 不以安装状态分组或打标签；两个业务页签加独立导入入口 |
| 同文件 §保存与激活、requirements 中的“仅保存，稍后激活 / 保存并激活” | 最后一步“确认配置”；唯一提交动作“添加员工 / 保存更改”，内部自动准备 |
| `requirements.md` §5 的“保存不安装，激活或首次工作才检查” | 正式提交立即检查并补齐；工作前仍可做健全性复核，但不是首次完成技能准备的主流程 |
| D13、D15 中要求用户分别操作保存与激活的旧交互解释 | 保留声明、全局复用、权限边界和执行快照；取消正常创建编辑流程中的独立激活步骤 |
| 打开编辑即建立持久化 RoleDraft；步骤变化也保存成内容草稿 | 仅真实业务内容差异产生编辑草稿，导航状态独立保存 |
| 未连接 Store 也可直接“仅保存”员工 | 可编辑并暂存草稿；只有所有所选技能能在本地可信满足时，才能离线正式提交 |
| 2026-10-26 十角色设计中的“首批模板不预选技能” | 官方角色预选经验证的基础技能组合；用户可直接沿用，也可取消、替换和补充 |

## 1.1 经典专家角色与语言补充（2026-10-26）

按[经典角色与双语设计](expert-role-catalog-v1.md)提供首批十角色：产品经理、架构师、Web UI 设计师、测试工程师、文案专家、技术文档专家、后端与集成工程师、前端工程师、数据分析师和 DevOps 工程师。每个角色均有中英文职责、输入、交付及验收标准、方法、边界和技能推荐理由；具体完整正文见[双语设计样例](examples/expert-roles.authoring.json)。保留旧角色 ID，发布新模板版本，不自动更改已有员工。

技能需求清单与已发布技能分开：编写源可标记待匹配能力，公共角色只引用可验证的真实固定技能。官方角色预选经过审核的基础技能组合，使用 `defaultSelected` 显式记录；core 是推荐优先级，不是强制安装，也不是客户端推导默认选择的规则。用户可以沿用、取消、替换或补充。文案与技术文档分工，设计与前端实现分工。官方角色的中文和英文共用身份、技能及版本，UI 语言切换不改员工正文、不生草稿、不换包；添加员工时固定配置语言，后续主动翻译作为可审阅更改。

## 1.2 默认技能组合与专业推荐（2026-10-27，覆盖旧不预选规则）

角色是“专业工作方式 + 经过验证的默认技能组合”。普通用户不需要先认识技能名称、搜索仓库或自行设计组合，选定角色并补充必要的专业方向即可沿用组合创建员工；配置技能步骤用于查看或调整，不要求逐项重新勾选。

- 官方负责选择真实技能、说明对应职责、检验组合内的重复或冲突，并用代表性工作验证效果。热门程度仅是候选发现信号；推荐依据包括任务适配、内容质量、维护、许可、宿主兼容及实际验证结果。不能只挂热门名称，也不能发布只有分工而无真实默认技能的官方专家模板。
- 角色详情直接展示“默认技能”、各自用途及推荐理由，其他推荐作为可选补充。查看不安装；明确添加时，一次性把同一已验证模板版本中 `defaultSelected=true` 的固定引用放入创建草稿。提交才自动准备，全成功后生效。
- 用户取消后，切步骤、换语言、刷新推荐或重新打开草稿都不得重新勾选。编辑、复制员工保留个人技能集合，不重新套用官方默认值。选择另一个角色起点并涉及覆盖现有填写时，需要明确展示将替换的内容。
- 角色执行任务时，宿主自动提供其已选固定技能及适用说明；模型无需用户再次输入技能名，应在相关工作前读取并遵循适用技能。无关技能不强行调用，缺依赖或技能不可加载应明确报告，不静默退化为通用回答并声称已使用技能。
- 以任务实际加载记录和可检查的工作结果验收默认技能组合；仅安装成功、把名称写入提示词或模型自称使用均不足以通过。不会把提示词约束宣称为模型必然遵循的保证。
- 自定义角色可以手工选择或采纳引导建议；零技能仍允许，但这是用户选择，不是官方专家模板的默认交付。环境限制不能通过静默删除预选技能规避；应说明原因并允许用户调整。

本次只修订设计；样例中的预选意图不使未解析技能变成可安装条目，真实制品选型与组合验证仍是发布前置条件。

具体推荐配置见[十角色开源技能选型](expert-role-skills-recommendations-v1.md)。阿里云角色接口需返回实际默认绑定、角色理由、何时使用、固定来源与环境/验证状态；不能由客户端写死推荐，也不能用源码已找到冒充安装或实跑通过。契约见[API 增量](role-skills-api-v1.md)。

## 1.2 Store 定期维护与 AI 匹配（2026-10-28）

用户确认 Store 统一维护并定期更新真实技能目录；用户主动请求时，AI 根据专家职责匹配可信候选并说明理由。默认推荐不实时上网搜索；首版不编造数值推荐指数或将仓库 Stars 称为技能使用量。审核更新、分阶段范围、隐私和验收见[Store 技能推荐运营设计](store-skill-recommendation-operations-v1.md)。官方模板的已审核默认技能组合继续按 2026-10-27 决定执行；AI 补充推荐不重置用户选择。

## 2. 对象及责任边界

| 对象 | 用户如何理解 | 边界 |
|---|---|---|
| 官方角色模板 | 配好专业工作方式与默认技能组合的起点 | 用户可调整；不覆盖个人员工；预选不等于已安装 |
| 技能目录条目 | 一项真实可取得的技能及来源、版本 | 不允许用能力名称假装可安装技能 |
| 角色推荐关系 | 此技能为什么适合这个角色 | 同一技能可对多个角色有不同理由；推荐刷新不改用户已选项 |
| 员工技能选择 | 这位员工工作时自动带入、相关任务默认使用的技能集合 | 无需每次点名；按任务适用性读取与使用；不授予项目或工具权限 |
| 待提交配置 | 用户已编辑但尚未生效的信息 | 与当前生效员工版本分开；草稿不影响真实任务 |
| 技能准备记录 | 本次提交实际完成到哪一步 | 宿主拥有；Store 不管理本地员工或机器安装状态 |
| 全局技能资源 | 多个员工复用的内容 | 移除声明/员工不卸载；同名不一定同来源同版本 |

官方负责角色、分类和推荐质量；Store 负责收集候选、审核发布、可验证分发和查询；Agent 负责选择、暂存、安装过程和配置生效；模型不能随意编造目录或来源。

## 3. 页面与主流程

### 3.1 入口和四步向导

保留“角色库 → 查看角色详情 → 添加为我的员工”，也允许自己设计。员工档案只读；“编辑员工配置”打开同一编辑器，不建立空修改草稿。

四步名称：选择起点 → 定义角色 → 配置技能 → 确认配置。模板和编辑可以跳过已确定的起点。最后一步只总结用户填写及技能选择，不重复介绍安装架构，不要求另行激活。

### 3.2 配置技能

页首“这个角色会什么？”；官方模板说明“已为这个角色配好推荐技能，可直接使用，也可调整”。主区为已选的默认组合，辅以“调整技能”“导入来源”；自定义角色按实际选择显示，不把空集合说成已配好。提交时自动准备。可选推荐展示少量匹配项；完整列表进入选择器，不将大量推荐堆在员工表单。

技能行：勾选、易读名称、用途、必要的来源归属、推荐理由、详情。名称和用途为主信息；推荐理由单独一句解释角色职责关联，如“适合你选择的架构评审方向，可补充依赖分析与方案取舍”。不把用途改写一遍，不凭 Stars 声称质量。内部 `curated / roles.architecture · v0.1.0` 移到详情来源区，主列表不展示内部 ID。

选择器：

1. “角色推荐”：按当前角色/所选方向展示官方维护的匹配结果，显示理由和推荐依据；切换方向不自动替换已选。
2. “全部技能”：名称/用途搜索、分类筛选、可继续加载；搜索和分页不清掉选择。
3. 独立“导入来源”：GitHub 仓库及可选分支/标签/提交、技能子目录，或本地目录。解析、预览名称用途和来源，再添加到选择。

“全部技能”包含可供用户选择的目录条目及已有个人来源，按可信身份去重，不显示“已安装”分组或标签。当前员工的旧来源和用户导入不因 Store 未收录而消失。无法稳定识别的旧来源保留为可检查项，不静默删除。

详情展示用途、适用场景、角色推荐理由、作者、官方开发/官方精选第三方标记、原始仓库、许可证、内容版本/提交、更新时间、支持平台及必要配置。暂无推荐理由的普通搜索结果不编造理由。外链与勾选分离；点详情不改变选择。

选择器中“完成选择”才应用本次变化；取消、Escape 或关闭返回之前选择。已选计数跨页签、搜索、分页累计；沿用现有 20 项上限，达到时说明原因但仍允许取消勾选。导入解析与缓存不等于安装；取消导入不修改员工，未引用快照按架构规则清理。

### 3.3 提交与准备

新建按钮“添加员工”，编辑按钮“保存更改”。前端校验后立即显示“正在准备员工…”，请求一经受理就可离开。宿主持久化本次提交和固定内容，再依次检查技能身份/所需版本、准备缺项、校验、应用配置。

- 不让用户逐项确认正常安装，不新增“安装管理”步骤。
- 全部可复用时直接完成，不为了展示动画延迟。
- 全部成功才显示“员工已添加”或“更改已保存”；准备好表示所选技能包已经校验且可被加载，不等于已运行真实任务或能力已验证，也不保证外部服务凭据、SSH 和工具运行环境已就绪。安装不自动执行第三方 setup 脚本；实际使用时按现有权限与环境检查处理这些条件，不能把服务器和凭据变成保存员工的统一前置步骤。
- 只修改名称/职责也复核已选技能；发现缺失则走相同准备流程。无业务修改不能触发安装或新增版本。
- 取消勾选只更新后续员工配置，原有共享技能保留。没有技能也可完成。
- 新配置不扩大已有项目授权；准备过程不触发业务任务。

### 3.4 真实进度与返回路径

当前提交区域显示总状态、已完成项数/总数、逐项阶段与失败原因。检查已满足的条目显示“已就绪”；不要求用户理解它是复用还是新安装。仅有字节总量和已下载量时才显示真实下载百分比；未知阶段显示文字及活动指示，不合成虚假总体百分比。

| 用户状态 | 反馈和操作 |
|---|---|
| 检查中 / 下载中 / 安装中 / 校验中 | 阶段、完成项数；可离开，不能重复提交同一配置 |
| 应用配置中 | 保持进度，可重新查看，不能提前显示保存成功 |
| 完成 | 成功反馈，进入员工档案；原任务保持原版本 |
| 部分失败 | 列出失败项和原因；“重试失败项”“返回调整技能”；成功项不重复下载 |
| 需要配置/不兼容/来源冲突 | 说明具体缺项或平台限制，提供明确处理入口，不报笼统安装失败 |
| 中断待恢复 | 显示已完成项和“继续准备”；核对真实安装后接续，不重放业务任务 |
| 并发配置冲突 | 提示员工已被其他窗口修改，保留当前填写并可比较/重新编辑；不覆盖最新版本 |

离开页面不停止宿主任务；我的员工中保留准备入口和状态。新建准备项不得伪装为可用员工，编辑准备项应同时明确“当前版本仍可用”。查看进度不得隐式重试。进程退出后不可声称后台仍运行；重开显示待恢复而非永久加载。

准备中的目标配置不可被后续输入悄悄替换；如用户选择“返回调整技能”，需先终止本次尚未应用的提交并保留可编辑草稿。若应用已完成，进入新版本编辑，不能回退已成功提交。已准备的共享内容不因终止而删除。

## 4. 草稿、内容差异和快照

编辑时以打开时的员工配置版本为基线。首次实际内容差异才创建持久化编辑草稿；已存在真实草稿时继续原草稿，提示正在编辑未提交更改。

业务差异包含名称、方向、职责、交付、方法、技能身份与固定来源/版本。导航步骤、页签、滚动、展开详情、推荐刷新、安装状态、时间戳不计入业务差异。无顺序语义的技能集合重新排序不算差异；来源或版本变化即使显示名相同也算。规范化规则与提交验证一致，不能靠过度 trim 消除有意义的文本修改。

改回基线后清除本次等价编辑草稿，保留导航位置可以单独持久化；不能删除其他窗口产生的更新。无修改保存按钮禁用或显示“无更改”，服务端也必须识别空提交。旧版自动产生的无差异草稿迁移时清理，真实内容差异保留。

新建与编辑不同：明确“添加为员工/自己设计/复制”开始的创建过程可保留起点草稿；查看模板或员工档案不建立草稿。复制生成新身份，不复制聊天、凭据、项目授权。AI 建议只有用户应用后才改变业务内容，迟到响应不能覆盖手工填写。

提交固定员工配置及技能来源/版本。正在执行的任务保留旧快照；下一次新任务在配置应用成功后使用新版本。新提交失败时不得先把旧员工状态改为不可用。版本并存不被当前全局技能同名覆盖破坏；不能并存时必须明确冲突，不能暗中升级所有员工。

## 5. Store 所需产品能力

此表定义功能责任，不假定已有 HTTP API。具体字段、版本协商和错误码以架构文档为准。

| 能力 | Agent 所需结果 | 不可省略的状态 |
|---|---|---|
| 官方角色目录与详情 | 稳定角色 ID、版本、多语言职责和推荐关联 | 空目录、缓存、更新失败、模板撤下 |
| 技能搜索/分类/分页 | 稳定技能身份、用途、来源、支持平台、可选版本 | 空搜索、下一页、加载失败、旧游标失效 |
| 按角色获取推荐 | 角色关联、理由、匹配维度、推荐更新时间 | 无匹配、角色改版、离线缓存、理由缺失 |
| 技能详情及版本解析 | 固定内容身份、原始来源、兼容与配置要求 | 版本下架、撤销、不可取得、校验失败 |
| 可验证包分发 | 固定版本包、内容校验、断点/失败恢复所需信息 | 网络错误、损坏、重试限流 |
| 来源导入 | GitHub 来源可解析，固定到提交和内容；本地由宿主预览 | 非技能目录、多技能仓库需选目录、来源移动或不可用 |
| 目录增量/刷新 | 新版本和更新时间、缓存有效性；结果与所选快照分离 | 过期数据提示，不自动替换员工配置 |

GitHub 收集属于 Store 运营流水线：候选发现 → 去重 → 解析能力/许可证/平台 → 分类 → 角色关联与理由审核 → 发布。Stars、增长和维护活跃度只做信号；抓取失败不撤回已发布可用目录。不能抓到即进入“官方精选”。公开目录中不加入本地路径、员工名字或项目资料。收集频率可配置，建议每日发现、审核后发布；具体运营频率仍需按配额及维护能力验证，不是本轮已确认 SLA。

## 6. 边界场景与视觉要求

- 推荐为空：说明暂未匹配，提供“浏览全部技能 / 导入来源 / 不添加技能继续”，不用虚构热门填满。
- Store 离线：可读可信缓存并标更新时间；可编辑/暂存。所选项本地均可可信满足可提交，否则保留待准备项和重试；不能把离线当空目录清空选择。
- 无模型服务：手工编辑、目录推荐和安装仍可工作。AI 起草不可用不阻断主流程。
- 被撤销来源、同名不同源、版本冲突、平台不支持：保留选中项及理由，阻止不符合条件的提交并定点处理，不强制用户去找旧“已安装”页签。
- 导入私有仓库或外部凭据不足：明确需要配置；不得把凭据放入员工表单或上传目录。继续其他编辑及已完成准备。
- 用 shadcn/Base UI 已有 Checkbox、Tabs、Sheet/Dialog、Progress、Alert 语义；不造复杂安装仪表盘。用途与理由各占明确层级，技术来源默认收起，失败原因就地可见。
- 系统字体、紧凑行距、现有圆角和主题 token；浅深主题状态都可辨，不只依赖颜色。支持长名称、中英文，主操作与勾选不被挤掉。
- 390px 宽与正常桌面宽均不水平溢出；窄屏详情单列；底部选择计数与完成操作稳定可达；200% 字号仍可操作。
- 键盘 Tab 可到搜索、页签、勾选、详情及提交；Space 勾选，Escape 关闭子面板并恢复触发器焦点。取消面板不丢外层草稿。
- 加载用局部骨架/阶段，结果刷新不抢焦点、不把列表滚回顶部；进度通过可访问状态区域播报，逐字节更新不反复打断读屏。

## 8. 待验证项与实施边界

待验证不等于要求用户重新决定。实施者先按架构契约做原型与测试，并把不满足之处报告在交付清单中：

- 现有安装器能否支持固定版本并存和真实下载进度；不能时必须调整内部存储，不能以同名覆盖满足界面承诺。
- GitHub 配额、许可证检查、平台兼容元数据及官方审核维护成本；推荐质量需实际样本验证，不能把示例工作法冒充热门。
- 旧安装来源的可追溯程度、缓存过期/撤销策略与离线可信准备边界；不足时保留旧数据并提示补来源。
- 后台进度事件在 macOS、Windows 的断线重连、重启恢复与并发场景。

当前代码事实：`WorkforceInputs.tsx` 仍有已有技能/Store/导入三页签；`WorkforceRoleEditor.tsx` 仍有激活标签和双提交；`role-drafts.cjs#createDraft` 打开即持久化；`service.cjs#activateOne` 针对已经保存的员工准备技能并使用同名冲突保护。它们都是待改造对象，不是本设计已经落实的证据。
