# 讨论主持人 INVALID_OUTPUT 排查与修复

## 已确认的事实

- 2026-11-04 11:32（Asia/Shanghai）一轮讨论在用户确认三个部署选项之后失败，状态为 `failed`、错误为 `INVALID_OUTPUT`，没有产生主持人步骤或任务修改。
- 最近几轮记录的规则版本仍是 `discussion-host-v3`。当时运行的主进程没有加载已经在源码中实现的 v4 任务读写能力，因此回复称看不到已保存计划、只输出文字与 Mermaid 提案。
- `INVALID_OUTPUT` 来自共享模型适配器；它原来把无效 SSE 事件、异常结束和 JSON 正文解析失败合并为同一个错误。返回正文没有持久化，无法从历史记录区分本次具体分支。
- 原适配器仅在提示词要求 JSON，没有使用 DeepSeek 的 JSON 输出模式，最终直接 `JSON.parse`。完整代码围栏、空白正文、语法错误均会失败。
- 经用户授权，用同一失败轮次上下文对原 DeepSeek 服务做只读重放；修复前一次重放成功（32.8 秒），没有稳定复现历史失败。因此不能声称已找到了历史正文中的具体非法字符或确定就是代码围栏。

## 修复

1. DeepSeek 的 Chat 对象输出启用 `response_format: {type: 'json_object'}`。依据官方文档：https://api-docs.deepseek.com/guides/json_mode/ 。该模式保证语法约束，不替代下游 Schema、来源、专家授权与任务版本检查。
2. 流式和非流式使用同一解析函数，仅兼容包住完整 JSON 的单层代码围栏。禁止从解释文字中截取对象、补引号、猜测或修补截断 JSON。
3. 主持人与任务引导明确启用一次格式重试，且仅重试未应用的模型推理。空／缺失／非法 JSON 正文可重试；断流、输出上限、异常结束、传输错误、业务校验失败不在此重试范围。沿用原截止时间与取消信号，最多两次模型请求。其他自动化不默认重试。
4. 失败保留已提交答案和已保存任务，向用户显示可理解的错误。主持人记录错误码和诊断阶段、原因、正文长度、尝试次数；不持久化模型原文或凭据。

- 原失败轮次上下文在修复后 18.8 秒完成，仅一次请求，确认启用了 JSON 模式；结构和引用来源校验均通过。重放仅调用模型，不触发任务服务、部署或执行。
- 使用合成项目与隔离数据库，DeepSeek 完成生成（14.9 秒）、仅解释（10.6 秒）、修改（18.5 秒）、状态查询（9.0 秒），实际项目执行次数为 0。
- 161 项测试通过：模型适配器、自动化与 workforce 回归。新增覆盖流式／非流式围栏、空响应、格式重试上限、取消、传输／结束错误、禁止从正文猜测决策、失败保留用户答案及继续对话、有效 JSON 仍必须通过业务校验。
