# 扩展工作区与统一管理：交互方案 v2

2026-10-23 · 用户已确认原型；首轮宿主实现与验证完成

本方案替代 unified-library.md 中「删除扩展业务列表、活动栏只打开管理中心」的决策。发现页顶部说明卡片已恢复；活动栏、业务入口、管理覆盖层及失效处理已落实到宿主。可点击原型位于 agent-flow/designs/extension-workbench/index.html，仍是使用虚构内容的评审稿；实际功能以宿主实现与下方验证记录为准。

## 产品定义

Ambleloft 是软件公司开发自己业务 Agent 的底座。扩展同时可以提供业务页面、工具操作、技能和后台能力。Agent 对话是入口之一，扩展的独立 UI 也是正式业务入口。不能把所有扩展都设计成「选择一段提示词」。

- Skill：描述工作方法、指令及声明式业务表单，主要在任务对话中使用。
- Extension：可提供自定义 UI 和 Node 后端，连接现有服务、工具、设备及其他执行环境；可以捆绑 Skill，也可以没有页面。
- 管理中心：负责发现、安装、创建、配置、权限、启停和卸载，不承担替代扩展业务 UI 的职责。

统一的是同一类操作的归属和行为，不是强迫所有操作经过一个页面。

## 现有契约与目标边界

核对依据：`specs/extensions/contracts/extension.schema.json`、`core/extensions/service.cjs`、`src/ExtensionSurface.tsx`。

- 现有包可声明一个 `contributes.home`，含 title、webRoot、entry、when；宿主用隔离的扩展页面承载 UI。
- 现有 `contributes.commands` 可声明 openHome；已提供的多个命令不等于多个独立页面。
- 旧的 `contributes.views` 属于兼容形态，不能据此向新扩展承诺 VS Code 完整的 View Container / Tree View 契约。
- 首轮按每个扩展一个业务入口复用 home，优先把已有页面体验做好。多个独立页面、可贡献侧栏树、跨业务子页深链接单列为后续契约设计，不先造 manifest 字段。
- 当前 ExtensionSurface 离开时关闭页面。原型中的业务状态保留是待实现目标，不能把原型页面切换理解为宿主已具备页面驻留能力。

```text
项目               扩展                           售后服务

```

原型中的「研发规范」是可选的未来业务页面示意，不表示现有 ai-rules 普通 Skill 已升级成扩展，也不要求其升级。

### 活动栏与侧栏

1. 活动栏「扩展」切换 activeGroup，侧栏立即切成扩展业务入口，项目列表不继续出现。
2. 首次进入：有可用业务页时打开第一个；之后恢复上次打开的有效入口，包括管理中心的上次位置。没有入口时展示扩展工作区空态，解释这里可承载什么，并提供「发现工具」。
3. 再次点击已选中的活动栏图标，可按既有侧栏规则收放；不重新加载正在使用的业务页面，不重置用户筛选或草稿。
4. 扩展入口来自受信任、已启用且具有 home 的安装项。标题优先 home.title，支持现有图标及多语言；同名时用扩展名补充区分。
5. 没有 home 的扩展及普通 Skill 只在管理中心和适用的聊天选择器出现，不制造空白业务页。
6. 有页面但暂不满足项目、配置或权限条件的入口保留可识别状态；点击后在主区说明缺项并提供前往设置/选项目的动作。不能悄悄打开另一业务，也不能把不满足条件当作已授权。
7. 侧栏底部固定「技能与扩展」进入唯一管理中心。分组侧栏模式采用同样的业务入口分组与管理入口，不另建一套行为。

### 主内容区

- 选择「售后服务」直接打开其业务 UI，而非扩展详情或安装管理页。日常操作不用先经过「已安装」。
- 宿主提供紧凑的页面标题、适用时的项目上下文，以及更多菜单中的「设置与权限 / 扩展详情」。业务筛选、列表、表单和动作由扩展页面组织。
- 设置/权限使用同一管理模块，以独立覆盖层承载，保留业务页并返回原入口。不得为工作区和管理中心各实现一套配置表单。
- 不假定宿主可以读取扩展任意 DOM 并保存表单。第一步要求扩展使用已有 storage 能力显式持久化草稿；页面驻留、离开前脏状态保护需要单独补契约与生命周期验证。
- 页面重开不得自动重放提交。停用、卸载和更新必须明确关闭/替换原页面；失效入口清除选择并回到安全落点。异常页面展示重开/设置，不无限自动重试。
- 切换页面不应停止任务或自动执行设备连接、提交工单等业务动作。后台生命周期与页面可见性分开处理。

## 管理中心

| 区域 | 回答的问题 | 行为 |
| --- | --- | --- |
| 已安装 | 我有哪些能力？ | 合并技能与扩展列表；页面扩展主动作是「打开」，Skill 和无页扩展提供适用的聊天使用动作；次动作进入详情与设置 |
| 发现 | 还能做什么？ | 恢复原顶部说明卡片、精选内容和详情；安装成功后根据能力提供打开页面或聊天试用 |
| 我的创作 | 我做到了哪一步？ | 回到对应任务继续需求、生成、安装与试用，不重新启动一个相同创建流程 |
| 创建技能 / 扩展 | 怎样制作自己的工具？ | 同一个技能大师引导；按需求选择 Skill、扩展、业务 UI、接入方式及配置项 |
| 从本地安装 | 我已有产物，如何装入？ | 技能目录、扩展包、开发目录统一归口，安装结果立即同步中心和扩展侧栏 |

发现页说明卡片原文及视觉恢复。卡片里的「描述你想做的事」调用同一创建流程；卡片可见时不同时显示顶部重复创建按钮。统一操作实现不意味着删除有价值的说明与上下文引导。

聊天 `$` 只选择本次任务要调用的能力，不负责打开业务工作区或安装管理。全局搜索的业务扩展结果主动作应打开页面；技能结果可选择在聊天中使用或查看详情；明确的「管理」动作才进入管理中心。

## 项目与权限上下文

售后、订单类页面可能不依赖项目，不能强制先选本地目录。研发和设备工具可能依赖本地、SSH 或 Docker 项目。

已核对：`extensionPage.context` 的 projectId 用于宿主判断 home.when；它不是扩展业务操作的自动绑定项目。现有 WebviewClient 的 HostContext 不暴露项目；项目级操作仍通过 `selectProject` 的宿主确认取得项目，然后将 projectId 显式传给操作，OperationRouter 验证项目及授权。

因此本轮只在有 home.when 的页面显示「入口项目」，说明它仅控制页面可用条件；不冒充业务数据范围。打开页面前先同步宿主上下文。切换入口项目先提醒保存并确认，随后关闭旧页、取消该页在途请求并重开；不会自动授予项目权限或重放提交。自动继承并展示业务项目的 SDK 契约留待后续单独设计。

页面可打开、配置已保存、权限已授权、业务服务可连接分别表示不同事实。宿主授权仍由宿主控制，服务端角色和对象权限仍由业务服务验证。进入页面或勾选项目不会扩大权限。

## 代表性走查

1. **售后服务**：发现说明 → 安装扩展 → 配置测试服务与凭据 → 侧栏出现售后入口 → 自定义页面查询工单 → 聊天三步登记 → 回到页面显式刷新查看结果。自动实时同步另行验证，不用动画冒充已有能力。
2. **ai-rules**：发现/本地导入普通 Skill → 聊天选择 → 审查集合与受管修复。其价值不依赖额外业务页面或 Node 服务；如果将来需要团队规则看板，再选做独立扩展。
3. **设备调试（规划案例）**：技能大师了解目标 → 生成带设置和业务 UI 的扩展 → 工具链路径与设备地址在配置中维护 → 在扩展页查看连接与调试状态。打开页面不自动写入或烧录设备；真实硬件链路未宣称实现。
